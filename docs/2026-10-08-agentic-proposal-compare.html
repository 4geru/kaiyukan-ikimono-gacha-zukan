結論

推奨: 3番をベースに、2番の「停止スイッチ」「評価の指標」「Webhook の二重処理防止」を足す。

3番はクイズのエージェントに触らない（「全部作ってから選ぶ」方式を残すという決定と矛盾しない）。/demo で提出要件の「ソーシャルログインを避ける」に答え、既存のロック表示（card.html）がようやく動く。合計 約6人日で、締切までの余裕はほとんどない。

3案に共通するコア

3体とも独立に同じ骨格へ収束した。自己採点も全員「自律性 5 → 8」。

次の一手エージェントユーザーの図鑑・正誤・解放状況を読み、次の行動を ADK エージェントが選ぶ
行動は許可リストenum で限定し、返り値もコードで再検証。範囲外は安全側へ
書き込みはコードだけエージェントのツールは読み取り専用。タイムアウト時は今の固定ルールへ戻す
判断を記録して見せる入力の要約・行動・理由・介入を Firestore と Cloud Logging に残す
ガードレールユーザー文の分離（インジェクション対策）、入力長と呼び出し回数の上限

3つの提案

PROPOSAL 1

次の一手を決める研究室

判断の主体をエージェントへ、判断の記録を審査員へ
行動 7種クイズ置き換え
  • 易しい／難しい出題・ヒント・知識の解放・水槽へ誘導・雑談・待つ
  • クイズを「計画 → 1問だけ作る → 自己検証」に置き換え（25〜40秒 → 約10秒）
  • 判断ログを agentDecisions に記録、ログインなしの agent-log.html
  • 「なぜこれ？」ボタンでジンベエが理由を説明
  • インジェクション対策・冪等性・回数上限
規模: 2.5＋1.5＋1.5＋1＋(0.5) 人日
PROPOSAL 2

次の一手を決める学芸員

判断の証跡が見える図鑑
行動 4種＋難易度クイズ置き換え
  • 出題・ヒント付き出し直し・未登録種への誘導・知識の解放
  • カテゴリと難易度を先に決めて1問だけ作る（約10秒）
  • agentRuns と LIFF の「博士がこの問題を選んだ理由」
  • 停止スイッチ AGENT_MODE=off/shadow/on（記録だけ取る段階導入）
  • 評価ハーネス: 20種×5パターンで行動分布・期待一致率・介入率・p95
規模: 2.5＋1.5＋1＋0.5 人日（計 約5.5）
PROPOSAL 3

研究室の次の一手

学習者の状態を読む案内エージェントと「観察ノート」
行動 4種クイズは触らない
  • 基礎の事実を話して解放・出題を勧める・未発見の仲間へ誘導・雑談
  • 「基礎を3つ話すまで出題しない」をコードで強制（当初の要件どおり）
  • 雑談に「いま見ている生きもの」の文脈を渡す
  • 観察ノート、quizHistory に選んだ理由を残す
  • パスコードで入れる /demo（体験と観察ノートを並べて表示）、レッドチーム10ケース
規模: 2.0＋1.0＋1.0＋1.5 人日（計 約5.5）

コードで確認した、3案共通の根拠

  • 回答時に tx.delete(pendingRef) し、quizHistory には category・question・choices・correctIndex・isCorrect しか保存しない → 選んだ理由（selectionReason）が回答と同時に消える（backend/src/server.ts 404〜437行付近）
  • frontend/card.html の renderKnowledge() はロック表示「？？？？」を描くが、knowledgeUnlocked はどこからも書き込まれない → 画面だけあって中身が埋まらない
  • characterChat.ts は contents: userMessage だけを渡す → 雑談は見ている生きものを知らない
  • 次に何をするかは handlePostback の action 分岐と固定のクイックリプライで決まる → フロー制御に LLM が関与していない

リスクと注意

  • 合計 約6人日で、締切までの余裕はほとんどない。/demo は遅れたら縮小版に切り替える判断点を 10/13 に置く
  • 機能を足すと、完成済みの紹介動画（176秒）の一部を撮り直す必要がある
  • 案内エージェントの結果は push で送るため、LINE の送信通数の上限を提出前に確認する
  • エージェントの判断の質は、評価スクリプトで事前に分布を確認しないと、デモで同じ行動ばかり出るおそれがある
