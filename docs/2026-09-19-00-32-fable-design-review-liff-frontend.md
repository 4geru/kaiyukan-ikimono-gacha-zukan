`docs/specs/784-liff-frontend/requirements.md`（Issue #784: LIFF Webフロントエンド）のドラフトを、設計フェーズへ進む前にFableへレビュー依頼した記録。

レビュー対象: requirements.mdの「決定事項」4点（採用演出／レアリティ3段階／サーバー側抽選への変更／館内の音・フラッシュ制約との整合）と、末尾「未確定事項」の切り分けが妥当か。

## 結論

このまま設計フェーズに進んでよいが、進む前に**2点はrequirements.md側で直すべき**（設計に転記すると設計側にも同じ矛盾が伝播するため）。それ以外の決定事項・未確定事項の切り分けは概ね妥当。

## 検証内容と具体的指摘

### 1. 採用演出（gacha-demo-03.html） — 妥当

特に問題なし。3案からの選定プロセスも明記されている。

### 2. レアリティ3段階60/30/10% — 妥当（実装と一致確認済み）

`frontend/gacha-demo-03.html` の `RARITY_TABLE` を実際に確認し、`weight: 10/30/60`（SSレア/レア/ノーマル）がrequirements.mdの表と一致することを確認した。779design.md 1.5節が「#783着手前には必須」としていた論点を先に固めた点は妥当。

### 3. サーバー側抽選への変更 — 方針は妥当だが、依存関係の穴あり

- `backend/src/server.ts` の `handleAnswerQuiz` のトランザクション内で `tx.set(colRef, { ..., rarity: "unknown", ... })` と**固定値のまま**であることを確認した。
- **問題**: 779requirements.mdの実装Issue表では#784（LIFF）の依存は`#780, #785`のみで、**#783（ガチャ演出・カード生成ロジック）は依存に含まれていない**。しかし決定事項3により「サーバー側の抽選ロジック実装」が#784の受け入れ基準の前提になった。実装issueが#783なのか#784なのか別issueなのかは末尾の未確定事項に送られているが、**依存Issue表そのものは更新されていない**。設計フェーズに進む前に、少なくとも「抽選ロジックをどのissueで実装するか」をrequirementsレベルで仮決めし、779requirements.mdの依存表に反映すべき（design.mdが書き上がった後で発覚すると手戻りが大きい）。
- **抜け**: `rarity: "unknown"`のまま#784が着手・テストされる期間（実装順序次第では十分あり得る）に、LIFF側が`rarity`を読んだ際の挙動が受け入れ基準に定義されていない。「Firestoreからrarityを読み取り、3段階のいずれかの演出を再生する」としか書かれておらず、"unknown"というenum外の値が来た場合のフォールバック（エラー表示か、暫定でノーマル扱いにするか）が未規定。開発初期に確実に踏む状態なので、受け入れ基準に1行足すべき。

### 4. 音・フラッシュ制約との整合 — 矛盾を発見（要修正）

決定事項4は「本実装では最大輝度到達時間を150ms以上に保つ（プロトタイプの`flash-pop`/`flash-pop-super`のタイミングを踏襲）」としているが、`frontend/gacha-demo-03.html`を実測すると事実と逆になっている。

```css
.flash-overlay.play  { animation: flash-pop 0.5s ease-out forwards; }
.flash-overlay.super { animation: flash-pop-super 0.7s ease-out forwards; }
@keyframes flash-pop       { 0% {opacity:0;} 12% {opacity:0.95;} 100% {opacity:0;} }
@keyframes flash-pop-super { 0% {opacity:0;...} 10% {opacity:1;} ... }
```

- `flash-pop`: 0.5s × 12% ≈ **60ms**でほぼピーク（opacity 0.95）
- `flash-pop-super`: 0.7s × 10% ≈ **70ms**でピーク（opacity 1）

いずれも150ms未満でピーク輝度に達しており、「プロトタイプのタイミングを踏襲すれば150ms以上になる」という説明は成立していない。「踏襲する」なら150ms未満であることを追認して基準自体を見直すか、150ms以上を要件にするならプロトタイプ側のアニメーション尺を伸ばす実装変更が必要になる、のどちらかをrequirements.md側で決め直すべき。数値根拠の点検不足であり、設計フェーズに引き継ぐ前に直したほうがよい。

なお「画面内CSSアニメーションは物理フラッシュと別物」という解釈そのものは妥当（他来館者への影響という779の制約趣旨とは論点が別）。

### 未確定事項の切り分けについて

- ビルド構成／ルーティング方式／魚博士ランクロジックはdesignフェーズ相当の論点で問題なし。
- Firestoreセキュリティルールは#785依存として既に779design.mdのFableレビューで指摘済み・追跡済みで問題なし。
- 「抽選ロジックの実装issue」だけは上記3節の通り、依存Issue表というrequirements側の成果物に影響するため、designフェーズに丸投げせず軽くでも方針を決めておくことを推奨。

## 対応

上記2点はrequirements.md（および779requirements.mdの依存Issue表）に反映済み。

- 決定事項3: 抽選ロジック実装は#783の範囲と明記し、779requirements.mdの依存Issue表に#784→#783の依存を追加。`rarity: "unknown"`時のフォールバックを受け入れ基準に追記。
- 決定事項4: 「プロトタイプのタイミングを踏襲」という誤った記述を削除し、実測値（60ms/70ms）を明記した上で、本番実装では150ms以上に伸ばす（プロトタイプのCSS変更が必要）と修正。
