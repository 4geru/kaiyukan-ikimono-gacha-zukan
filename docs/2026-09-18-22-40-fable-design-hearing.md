# Fableヒアリング: 現状の設計と今後の方針（2026-09-18 22:40）

海遊館いきものガチャ図鑑の現状実装（MVP: 識別→Flex Message→クイズ）と、requirements.md に書かれている残りの機能群について、Fableに技術顧問役として評価・懸念・優先順位付けをヒアリングした記録。

## ヒアリング時点の状況

- 実装済み: LINE Botに案内板写真を送信 → Gemini Visionで海遊館243種と照合し候補特定 → Flex Messageで候補提示・選択 → 選ばれた魚の4択クイズをGeminiが生成・出題 → 正誤判定して返信、という一往復のみ
- 未実装（requirements.mdに記述のみ）: Firestore永続化、LINE Login、LIFF Webフロントエンド、ADKによるマルチエージェント化、年齢層対応、ガチャ演出とレアリティ、Nano Banana Proでのカードイラスト生成、「魚博士」成長システム、家族の思い出振り返り動画（別機能）

## 1. 今のMVP設計は妥当か

コンセプト実証としては妥当だが、作り直しが確実な設計上の借金が2つある。

- `server.ts` の `pendingQuizByAnimalId` はグローバルな `Map` で animalId のみをキーにしている。Cloud Runは複数インスタンスにスケールしうるため、別インスタンスに当たった瞬間にクイズ状態が消える。より致命的なのは、**どのハンドラでもLINEのuserIdを取得していない**こと。今後Firestoreに進捗・年齢層・コレクションを保存する設計は全てユーザー単位が前提なので、後付けするより今のうちに `event.source.userId` を全フローに通す設計に変えたほうが手戻りが少ない。
- `identifyFish.ts` のマッチングは正規化＋部分一致（`includes`）のみで、confidence scoreも同名種の衝突処理もない。243種の中には和名が似た種が存在するため、誤マッチ検知・複数候補提示のロジックを固めないと識別精度がデモの成否を左右する。

良い点: Gemini呼び出しに`responseSchema`で構造化出力を強制している点、モジュール分割が薄く読みやすい点。

## 2. 残機能の優先順位

**優先すべき**:
1. LINE Login + 最小Firestore（ユーザー識別基盤。1.の設計借金の解消も兼ねる）
2. 「基礎情報を話してからクイズ解禁」という対話フロー自体の実装 — 審査基準の「自律性」を実証する唯一の要件なのに、現状のMVPには影も形もない（識別→即クイズの一直線）

**思い切って削るべき**:
- 「家族の思い出振り返り動画」は別機能として明記の通り価値提供の軸が違うので即カット推奨
- 年齢層別の言い回し調整は「事実は変えず表現のみ変える」軽量要件なので後回しでも実害は小さい
- ADKのフルマルチエージェント構成（コーディネーター＋4サブエージェント）は導入工数・デバッグリスクが大きい割に審査員に見える差分は「対話が自律的に見えるか」だけ。時間が厳しければツール呼び出し付きの単一エージェントで自律性を体現し、ADKへの正式移行は後回しにする判断もありうる
- Nano Banana Proでの243種×レアリティ事前生成も、デモで見せる種数（数十種程度）に絞ってコスト・時間を圧縮すべき

## 3. アーキテクチャの脆さ

- 前述のインメモリ状態が最優先の脆弱点。Firestore移行前に複数人が同時にデモを試すと簡単に壊れる
- LINE Webhookの応答はreply tokenの制約（数十秒）があるのに、Gemini呼び出しにtimeoutもリトライも未実装。今後ADKで複数エージェントホップを挟むと応答時間がreply token期限を超えるリスクが現実的に高まる。重い処理は即時ACK＋push messageへの切り替えを検討すべき
- `package.json`が`typescript: ^7.0.2`、`@types/node: ^26`という、Fableの知る限り異例に先行したバージョン指定になっている、との指摘（※このセッション内で`npm view`により実在する最新公開バージョンであることは確認済み。架空のバージョンではないが、ハッカソン直前にビルドが壊れるリスクを避けるため安定運用を優先するなら固定を検討）
- LINEチャットでの学習進捗をLIFF側にリアルタイム反映する要件（Firestoreでの同期）はまだ設計ドキュメントがなく、実装コストを過小評価しがちな箇所。AI部分より同期の実装の方が手間がかかる可能性がある
- Issue依存関係（#782は#780+#781完了後、#784は#780+#785完了後）はクリティカルパス上のどれか1つが遅延すると後続が連鎖的に詰まる構成。並列ワークストリームの進捗管理を意識的にやらないと終盤の統合で破綻する

## 4. 審査基準に照らして

- **新規性・有効性**: 海遊館公式データに基づく現地体験というコンセプト自体は具体性があり良い
- **自律性・エージェントらしさ**: 最大の弱点。現状のMVPは「識別→選択→クイズ→正誤判定」という完全に決定論的な一本道パイプラインで、LLMがフロー制御に関与する場面が一切ない。requirements.mdが謳う「気まま」な対話展開・クイズ出題タイミングの自律判断・理解度に応じた難易度調整はすべて未実装。このままデモに臨むと「LLM APIを2箇所で叩くルールベースのボット」に見えるリスクが高い
- **実装品質・拡張性**: 今ある範囲のコード品質は良好だが、マルチユーザー・永続化が未実装のため「拡張性がある」と主張する材料はまだない

## 5. その他の指摘

- 海遊館JSONは調査メモ自身が「非公式API、公開プロダクト化するなら事前確認が望ましい」と明記している。ハッカソンでは問題ないが、デモ・提出資料でPOC前提であることに触れておくと誠実。アクセス頻度は既にローカルJSONキャッシュ化済みで良い対応
- レアリティ判定基準・魚博士ランクのロジックが「未確定事項」のまま残っており、design.mdで骨格を決めないと#783（ガチャ演出）の実装が手戻りになる。早めに詰めるべき

## 総合すると次にやるべきこと

1. クイズ状態管理をuserId込みで作り直し、Firestore移行を前倒しする（現状のインメモリ設計はデモでも壊れうる）
2. 「基礎情報を話してからクイズ解禁」という対話の自律フローを、フルADK抜きでもいいので最小実装して審査基準「自律性」を可視化する
3. スコープを絞る（動画振り返り機能を削除、カード事前生成を数十種に縮小）ことでクリティカルパス上の統合作業に時間を確保する
