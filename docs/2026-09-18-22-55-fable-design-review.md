# Fableレビュー: design.md（Firestore構造・識別精度・クイズのエージェント化）（2026-09-18 22:55）

Opusが作成した `docs/specs/779-ikimono-gacha-zukan/design.md` を、前回のヒアリング（`2026-09-18-22-40-fable-design-hearing.md`）で指摘した3つの懸念が解消されているかという観点でFableにレビューさせた記録。

## 1. userId伝播・Firestore構造は懸念を解消しているか

解消できている。`event.source.userId`を全ハンドラの先頭引数に通す方針、`pendingQuiz`を`collection`から型的に分離した設計、Firestore一択の判断（インメモリMapは単一インスタンスでも壊れると明言）はいずれも妥当。

ただし実装時に詰めが必要な点が2つ:
- `handleAnswerQuiz`は「`pendingQuiz`を読む→正誤判定→`pendingQuiz`削除＋`collection.askedQuizCategories`更新」という複数回のFirestore操作になるが、design.mdはトランザクション/バッチ化に言及していない。LINE Webhookの再送時に二重更新（`askedQuizCategories`への重複追記など）が起きうるため、`runTransaction`かバッチ書き込みにすることを実装時に明記すべき
- LIFF側が`users/{lineUserId}/collection`を読む前提（要件の「リアルタイム同期」）なのに、Firestoreセキュリティルールへの言及が一切ない。#785側で読み書き権限を決めないと#784（LIFF）着手時に手戻りになる

## 2. 識別マッチングの改善方針

妥当。confidence申告、`findMatchingAnimals`への複数形化、3文字未満の部分一致を除外する閾値、優先順位を下げるが除外はしないという設計は、元の「1件を機械的に決め打ちする」欠陥を的確に潰している。

補足: confidenceの低い部分一致まで候補リストに全部残す設計だと、名前が類似する種が多い科（ハゼ類など）でカルーセルが長くなりすぎる可能性がある。上位N件（例: 5件）に絞るキャップを実装時に入れるべき（設計方針への反対ではなく実装時の詰め）。

## 3. クイズのエージェント化は「見せかけの自律性」になっていないか

**方向性は妥当。ただし1点、実装を誤ると本当に見せかけになる具体的なリスクがある。**

design.md 3.6節の型定義では`consideredCategories`が最後のフィールドに置かれている。これがそのまま`responseSchema`の`properties`宣言順になると、Geminiの構造化出力は宣言順に近い順でJSONを生成する傾向があるため、モデルは先に`category`/`selectionReason`/`question`を確定させてから、最後に「検討した候補一覧」を後付けで埋めることになる。これは「複数候補を検討してから選ぶ」自律的な意思決定ではなく、**結論を先に出してから理由をでっち上げる後付け正当化**であり、懸念していた「見せかけの自律性」そのもの。

```json
// 悪い例（design.md 3.6の型の並び順のまま schema化した場合）
{ "category": "...", "selectionReason": "...", "question": "...", "consideredCategories": [...] }

// 良い例（推論を先に、結論を後に）
{ "consideredCategories": [...13件...], "category": "...", "selectionReason": "...", "question": "..." }
```

→ **実装時、`responseSchema`の`properties`宣言順を「`consideredCategories` → `category` → `selectionReason` → `question`」にすること。** design.mdに一行足すだけで済むが、抜けると指摘した懸念がそのまま再現する。

範囲についての指摘: この設計が解決しているのは「クイズのどのカテゴリを出すか」という**出題内容選択の自律性**のみ。requirements.mdの「対話学習」セクションが本来求めていた、**「基礎情報を一通り話すまでクイズを保留する」という会話フロー全体の自律的な進行管理**には、design.mdは範囲外として一切触れていない（design.md冒頭で対象範囲を3点と明記しており意図的な絞り込み）。今回の設計は当初の懸念の一部（出題内容の多様性）は強く解消するが、審査員が「自律性」と聞いて想像するであろう会話全体のフロー制御はまだ空白。次のイシューで別途設計すべきと明示しておくと、後で「解消したはず」の認識ズレを防げる。

内容面の補足: 13カテゴリのうち「郷土料理」「海外の小ネタ」「進化の歴史」は生き物によっては実質的に語ることが薄い（クラゲに郷土料理、地味な展示魚に進化の歴史、など）。Geminiが弱い候補を無理に選んでしまうと豆知識の質が落ちるため、数種でプロンプトを試して薄いカテゴリが実際に選ばれていないかスポットチェックを推奨。

## 4. Firestore書き込みタイミングのスケジュールリスク

設計判断（レイテンシよりも正しさ優先でFirestore一択）自体は正しい。ただし「候補選択→13カテゴリ検討の重いGemini呼び出し1回→pendingQuiz書き込み」が同じreply token猶予内で直列に走る。往復回数を1回に減らした判断（3.1節）は正しい方向だが、13カテゴリ分の候補生成は以前の単一クイズ生成より出力トークン量が増えるため応答時間は伸びる可能性が高い。設計は「往復回数を増やさない」ことだけをレイテンシ対策としているが、単発呼び出しでも出力が重くなれば同じ問題が起きうる点は明記されていない。実装後に実測し、reply tokenの猶予に対して余裕があるか検証すべき。

## 5. 未確定事項（レアリティ・魚博士ランク・年齢境界値）は今決めるべきか

後回しで問題ない。Firestoreスキーマ側はいずれも`string`/`enum`型で受け口だけ用意されており、値そのものの確定はこの3設計の実装をブロックしない。ただし`rarity`の抽選テーブルは#783（ガチャ演出）着手前に必須なので、「このdesign.mdでは決めない」だけでなく「#783着手前に決める」と依存関係として明示すべき。

## その他、実装着手前に直しておくべき点

- `responseSchema`のプロパティ宣言順を明記する（上記3の指摘、最重要）
- `handleAnswerQuiz`のFirestore操作をトランザクション/バッチにする
- Firestoreセキュリティルール（LIFFからの読み取り範囲）を#785の設計に明記しておく
- LINE Webhook再送時の冪等性（同じイベントの二重処理）は今回もdesign.mdで触れられていない。ハッカソン規模なら許容できるが、少なくとも認識した上で見送る、という一言があるとよい

## 総合評価

3つの懸念のうち、(1)userId/状態管理と(2)識別精度は設計として妥当に解消されている。(3)自律性は方向性は良いものの、**schemaのフィールド順序という1行の実装詳細を間違えると意図が反転する**という具体的な地雷があり、かつ「出題カテゴリの多様性」止まりで「会話フロー全体の自律進行」までは踏み込んでいない点を、実装前に共有しておくことを推奨。
