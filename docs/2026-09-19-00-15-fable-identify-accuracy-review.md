# Fableレビュー: 魚識別マッチングの精度低下・実データ検証（2026-09-19 00:15）

ユーザーから「画像の検出精度が悪い」という指摘を受け、`images/guide/`配下20枚のバッチテスト結果（疑わしい誤マッチ複数）をFableに提示し、design.md 2章の改善設計で解消できるか、実際に`data/kaiyukan-animals.json`をクエリして原因を特定してもらった記録。

## 実データ検証で判明した事実（最重要）

| 誤マッチ例 | 実際のデータ | 原因 |
|---|---|---|
| ハリセンボン→ヒトヅラハリセンボン | 「ハリセンボン」自体が243種に実在（index103）。「ヒトヅラハリセンボン」も別entryとして実在（index1、配列の先頭近く） | `Array.find`の**配列順バグ** |
| ウツボ（モヨウタケウツボ） | 「モヨウタケウツボ」は243種に存在しない。「ウツボ」のみ実在 | **データ欠落**（正解が存在しない） |
| ツバメウオ→ヒメツバメウオ | 「ツバメウオ」単体は243種に存在しない。「ヒメツバメウオ」「ナンヨウツバメウオ」のみ実在 | **データ欠落** |
| シマアジ→マアジ | 「シマアジ」は243種に存在しない。「マアジ」のみ実在 | **データ欠落** |
| ハナゴイ→アカネハナゴイ | 「ハナゴイ」単体は存在しない。「アカネハナゴイ」のみ実在 | **データ欠落** |
| クエ→ヒメフエダイ | 「クエ」は243種に完全一致で存在する。「ヒメフエダイ」は名前・学名・英名いずれも文字列としてクエと重ならない | **おそらくGemini側のOCR誤読**（マッチングロジックの問題ではない） |

ハリセンボンの例を検証した結果、決定的な原因が判明: 「ヒトヅラハリセンボン」が配列index1、正解「ハリセンボン」がindex103にあり、`identifyFish.ts`の`findMatchingAnimal`は`Array.find`で完全一致か部分一致かを区別せず単一条件式で先頭から探すため、本来の完全一致（index103）に辿り着く前に、より劣る部分一致（index1）でヒットして即座に返してしまっている。**「短い文字列が誤って含まれる」現象ではなく、「配列の並び順次第で、完全一致より品質の劣るマッチが先に採用されてしまう」という、より根の深いロジックバグ。**

## 1. design.md 2章の改善で誤マッチ例は解消されるか

**一部だけ。この切り分けが重要。**

- **解消される**: ハリセンボンのように「正解が243種に実在するのに、配列順のせいで劣った部分一致に負けている」ケース。design.md 2.2節の`findMatchingAnimals`を**配列全体をスキャンしてから**優先順位でソートする形で実装すれば直る。ただし「完全一致が見つかった時点で即returnし、部分一致は完全一致が0件の時だけ探す」のような早期リターン実装にすると、同じ配列順バグを形を変えて再現するリスクがある。**「243件全部をフィルタしてから完全一致→confidence高→confidence低の順にソートする」という実装にすることをdesign.mdに明記すべき**（現状の2.2節は「全件スキャンが前提」という点を明示していない）。
- **解消されない**: ウツボ/ツバメウオ/ハナゴイ/シマアジのように、**パネルに書かれた種そのものが243種データに存在しないケース**。マッチングアルゴリズムの問題ではなくデータカバレッジの問題なので、どれだけ精度を上げても「正解」自体が存在しない。design.md 2章はこのクラスのエラーへの対応を規定していない（優先順位を下げて末尾に回す、とはあるが、候補が1件しかない場合は末尾に回す相手がおらず、結局誤った1件が単独候補として出る）。**これは設計の見落とし。** 低品質な部分一致しかない場合は、(a) 候補に出さず「見つからなかった」扱いにするか、(b)「もしかして」のような明示的な不確実性表現でユーザーに提示するか、をdesign.mdに追記すべき。今のままだと誤情報を確定情報として自信満々に提示してしまい、requirements.mdの「事実を捏造しない」方針にも反する。
- **解消されない（マッチングの範囲外）**: クエ→ヒメフエダイのように、**Gemini自体がパネルの文字を読み間違えている疑いがあるケース**。「クエ」は243種に完全一致で存在するのに誤った候補が出ている以上、マッチング側のバグでは説明がつかない。文字列マッチング改善だけで満足せず、**Gemini抽出結果（`extractedSpecies`の生の中身）をログ出力して、マッチング前の生読み取り結果を確認する**ことを強く推奨。

## 2. `matchType: exact/partial`区別だけで十分か

**方向（正引き/逆引き）の区別よりも、優先度の取り方（全件収集→ソート）の方が本質的。** 今回確認した実例では、正引き（animal.nameが短くextractedに含まれる: ウツボ⊂モヨウタケウツボ）と逆引き（extractedが短くanimal.nameに含まれる: ハリセンボン⊂ヒトヅラハリセンボン、ツバメウオ⊂ヒメツバメウオ）の**両方向で問題が起きている**。日本語の魚種名は属・科レベルの一般名に修飾語を前後に付けて複合語化する命名慣習があるため、片方向だけ許容する非対称ルールでは不十分。

追加で効く具体策2つ:
- **完全一致の絶対優先**（最優先。方向の区別より効果が大きい）
- **長さ比を使った類似度フィルタ**: `1 - 編集距離 / max(len(a), len(b))` のような相対類似度を計算し、閾値未満（目安0.7〜0.8）の部分一致は候補から除外する。design.md 2.2節の「正規化後3文字未満は除外」という長さの絶対値による閾値は、実例のほとんど（ハリセンボン6文字、ツバメウオ5文字、ハナゴイ4文字）を素通りしてしまうため**ほぼ効いていない**。文字数の絶対値ではなく、抽出文字列と候補文字列の長さの「比」で見るべき。

## 3. 実装順序（ローカル修正→20枚バッチ再テスト）は妥当か

妥当。ただし精度改善と同時に3点追加すること:

- バッチテストスクリプトに、**マッチング前の`extractedSpecies`生データもログ出力**する（クエのケースのように「読み取りミス」と「マッチングミス」を切り分けるため）
- Geminiの生成は既定でtemperature>0の非決定的な処理なので、**同一画像を複数回（例: 3回）実行して結果が安定しているか**確認する。1回のパスで「直った」と判断すると、たまたま通っただけの可能性がある
- `guide-panel-sample-images.md`の「内容」列はパネルの要約であり逐語的な正解データではない。特に「広島湾七大海の幸」パネルのように曖昧に書かれているものは、直す前に写真から正確な正解種名リストを確定させてから before/after を比較すること。曖昧な正解と比較すると「直った」つもりが実は測定誤差、ということになりかねない

## 4. その他の見落としがちな点

- `Array.find`の配列順依存バグは、この243種JSONの**配列順そのものに再現性がある**（kaiyukan公式サイト側のCMS順であり、アルファベット順でも分類順でもない）ため、今後データが更新されて配列順が変わると、同じロジックでも別の誤マッチパターンが新たに出現しうる。実装は「配列順に依存しない」形（全件スキャン→スコアでソート）に必ずしておくべき。
- 243種データの中に「マアジ」を含む無関係な名前（`ヤマアジサイ`、植物）が存在することも確認した。魚類・軟体動物とは全く無関係なカテゴリのエントリまで同じ配列でマッチング対象になっている点も、閾値なしの部分一致では事故の種になる。`classification`（分類）でGeminiの抽出対象を魚類・無脊椎動物などに絞ってから照合する、といった一段のフィルタも安全策として有効。
- 現在の`buildCandidatesFlexMessage`は候補が1件だけの場合、確認の余地なくそのまま1件のバブルを見せる実装。「データカバレッジが無いのに唯一の部分一致だけ出てしまう」ケースに対応するなら、確信度に応じてUI側の見せ方（「もしかして」の一言を添える等）も合わせて変える必要がある。マッチングロジックだけ直してもUIが「確定情報」の体裁のままだと、ユーザー体験としての問題は残る。
