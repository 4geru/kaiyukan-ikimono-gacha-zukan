# Requirements — 年パスの人向けの来館ログ（水族館へ行った日を記録して振り返る）

Issue: [#830](https://github.com/4geru/tweet-bookmark/issues/830)（親: [#779](https://github.com/4geru/tweet-bookmark/issues/779)）

## 目的

年パスで何度も海遊館に通う人が、**「いつ行って、その日に何を見つけ、何を学んだか」を後から振り返れる**ようにする。今の図鑑は「何を持っているか」（種の一覧）しか分からず、「いつ・どの日に」の流れが残らない。来館ごとにその日の発見・クイズをまとめ、エージェントがその日のハイライトと振り返りの一言、次の来館の提案を添えて、**翌日の海遊館の開館時刻に LINE へ push で届ける**。

提出スライド・提出記事の「これから作りたいこと」の2つ目（1つ目の思い出動画は #787）。届けたい人の1つ目「水族館が大好きな人（旅行先でも水族館を探す・年パスで何度も通う・ダイビングでも潜る）」向け。

**今回は海遊館に絞る**（2026-10-08 ユーザー決定）。他館は将来の拡張とし、来館の記録に館 ID を持たせて足せる形だけ残す。

審査基準との対応:

- 課題の新規性と有効性: 「その場の即時報酬（ガチャ）」に加え、通い続ける人に「積み重ね」を見せる
- 自律性・エージェントらしさ: その日の記録からハイライトを選ぶ・振り返る・次を提案する判断をエージェントに任せ（状況判断）、事実の集計と候補の範囲はコードで縛る（管理制御）。判断の理由を残す（可観測性）。座標を扱わず本人だけが読める（セキュリティ）
- 実装品質と拡張性: 来館の記録に館 ID（今は海遊館固定）を持たせ、他館へ広げられる形にする

## 前提（コードで確認済み）

### いま記録されているもの

- **図鑑登録**: 候補の生きものを選ぶと（`server.ts` の `handleSelectFish`）、`users/{uid}/collection/{animalId}` に初回なら `name`・`firstFoundAt`・`updatedAt`・`rarity`・`knowledgeUnlocked`・`completed` を作る。**2回目以降は `updatedAt` を上書きするだけ**で、再発見した日の履歴は残らない
- **クイズ**: 回答すると `users/{uid}/animals/{animalId}/quizHistory/{自動ID}` に `category`・`question`・`choices`・`correctIndex`・`askedAt`・`isCorrect` を残す（`handleAnswerQuiz`）。同時に `collection` の `updatedAt` も上書きする
- **写真**: `handleImageMessage` で GCS の非公開バケットに `line-images/{messageId}.jpg` として保存するが、**Firestore にはユーザーとの紐づけも撮影日時も記録しない**
- **位置情報**: `handleLocationMessage` は座標から最寄りの水族館と経路を返すだけで、**座標を Firestore にもログにも出さない**方針（コメントに明記、#789）
- 「来館」「訪問日」を表す概念・データは無い

### 識別と館の範囲

- 写真の識別は Firestore の `animalMaster`（**海遊館の243種のみ**）と照合する（`identifyFish.ts`）。図鑑の操作から自動で判定できるのは海遊館の来館だけ
- 関西15館のマスタ `backend/data/kansai-aquariums.json` があり、海遊館は `id: "kaiyukan"`。各館に `id`・`name`・`prefecture`・`address`・`lat`/`lng`・`station`・`stationCode`・`access`・`url` を持つ。**開館時刻・休館日の項目は無い**

### 時刻・push・LIFF・ルール

- Cloud Run のプロセスの TZ は UTC で、日時は JST に明示変換している（`nearestAquarium.ts` の `toJstDateTime`）。来館の「日」も JST で区切る必要がある
- 定時実行の仕組み（Cloud Scheduler 等）は今は無い。`pushMessage` は `server.ts` で、イベントへの応答の後追い（解析中・考え中の後に結果を送る）にだけ使っている
- LIFF 図鑑（`zukan.html`・`card.html`）は LINE ログイン → `/auth/line` のカスタムトークンで Firebase にサインインし、`shared/firestore-client.js` の `getUserDoc`・`getCollectionEntry`・`watchCollection` で読む
- `firestore.rules`: LIFF からは本人の `users/{uid}`（get のみ）・`collection`・`quizHistory` の読み取りだけを許可し、書き込みはすべて拒否。それ以外のパスは明示しない限り読めない（新しいパスを読ませるならルールの追加が要る）

## 想定ユーザー

- **年パスで海遊館に通う人**: 月に何度も来る。毎回すべては回らず、その日に気になった水槽を見る。「前回いつ来た？」「今日は何が新しかった？」を知りたい
- 子ども連れの家族（当初要件 #779 の小学生）: 親が後から「この日はジンベエザメを見たね」と振り返る

## ユーザーの決定（2026-10-08）

| 論点 | 決定 |
| --- | --- |
| 対象の館 | **海遊館だけ**。他館は将来の拡張（来館の記録に館 ID を持たせて拡張できる形は残す） |
| 来館の判定 | 自動＋申告。その日（JST）の図鑑登録・再発見・クイズ回答で自動。Bot を使わなかった日は申告で記録。あとから取り消せる |
| 振り返りを届けるタイミング | **翌日の海遊館の開館時刻に自動で push** |
| 家で過去の写真を送ったときの誤判定 | 自動で記録し、ユーザーが後から取り消せる |
| 写真の表示 | 初版は出さず、図鑑の公式画像で見せる |
| 過去データの取り込み | 取り込む（`firstFoundAt` と `quizHistory.askedAt` から、初回発見とクイズだけの来館として復元） |

## エージェントの判断とコードの縛り

| 部分 | 担当 | 縛り・フォールバック |
| --- | --- | --- |
| 来館日の確定、発見数・新種数・クイズ正答数・通算来館回数の集計 | **コード** | 事実は Firestore の記録からだけ数える。LLM に数えさせない |
| その日のハイライト（生きもの1つ）を選ぶ | **エージェント** | 候補はその日の記録にある animalId だけ。候補外を返したらコードで捨て、規則（その日の新種のうち最初に見つけたもの → 無ければ最初の記録）で選ぶ |
| 振り返りの一言（キャラの掛け合い） | **エージェント** | 前回の来館との差（初めての新種・連続正解・久しぶりの来館など）をコードが渡し、それを根拠に書かせる。数値はコードが渡したものだけ使う |
| 次の来館の提案（まだ見ていない展示エリア・生きもの） | **エージェント** | 候補は `animalMaster` に実在し、まだ図鑑に無い種／まだ行っていない展示エリアからコードが絞る。候補外は捨てる |
| 判断の記録 | **コード** | ハイライト・提案の理由、エージェント／規則のどちらで決めたか、候補外で捨てたかを来館ログに残す |

## 受け入れ基準（EARS）

### 来館の記録

1. system SHALL 来館を「ユーザー × 日付（JST）× 館 ID」の単位で1件として持つ。今回の館 ID は海遊館（`kaiyukan`、`kansai-aquariums.json` の `id` と同じ値）に固定する
2. WHEN ユーザーが図鑑登録（初回発見）または再発見をする THEN system SHALL その日（JST）の海遊館の来館に、その生きもの・時刻・初回発見かどうかを追記する（無ければ来館を作る）
3. WHEN ユーザーがクイズに回答する THEN system SHALL その日（JST）の海遊館の来館に、生きもの・カテゴリ・正誤を追記する
4. system SHALL 再発見の記録を来館ログに残す（今の `collection` は `updatedAt` を上書きするだけで履歴が消えるため）
5. WHEN ユーザーが「今日は海遊館に行った」と申告する THEN system SHALL その日（JST）の海遊館の来館を記録する（発見・クイズが0件の来館として）
6. system SHALL 申告では当日の来館だけを受け付ける（過去の日付の申告は受け付けない。未決論点3）
7. system SHALL 来館が自動か申告かを区別して記録する
8. system SHALL 同じ日の海遊館の来館を重複して作らない（Webhook 再送・連続操作・自動と申告の両方でも1件）
9. WHEN ユーザーが来館の取り消しを選ぶ THEN system SHALL その来館を振り返りの対象・来館回数から外す（図鑑の登録・クイズ履歴そのものは消さない）
10. WHEN 来館ログを導入する THEN system SHALL 既存ユーザーの `collection.firstFoundAt` と `quizHistory.askedAt` から、日付（JST）ごとの海遊館の来館を復元する。復元した来館には「復元」の印を付け、再発見が含まれないことが分かるようにする。復元した過去の来館には push を送らない

### 振り返り（エージェント）

11. WHEN 振り返りを生成する THEN system SHALL コードで集計した事実（発見数・新種数・クイズの正答数・通算来館回数・前回の来館日）を確定してからエージェントに渡す
12. system SHALL エージェントにハイライト（生きもの1つ）・振り返りの一言・次の来館の提案を、それぞれ理由付きで決めさせる
13. IF エージェントがその日の記録に無い生きものをハイライトに選ぶ、または実在しない種・エリアを提案する THEN system SHALL その結果を捨て、規則で選び直したことを記録する
14. IF エージェントが時間内（目安10秒）に返さない、または失敗した THEN system SHALL 規則によるハイライトと定型の一言で振り返りを作る（push を止めない）
15. system SHALL 振り返りの一言に、コードが渡していない数値・日付を書かせない（プロンプトで指示し、出力に渡していない数字があれば定型文に切り替える）
16. IF 申告だけの来館（発見・クイズが0件）である THEN system SHALL ハイライトを選ばず、来館したこと・通算来館回数・次の来館の提案だけで振り返りを作る
17. WHEN 振り返りを生成する THEN system SHALL 結果（ハイライト・一言・提案・理由・決めた主体）を来館ログに保存する。日付が締まった後（翌日）に作るものを確定版とし、同じ来館について作り直さない

### 翌日の開館時刻の push

18. WHEN 海遊館の来館があった日の翌日（JST）、海遊館の開館時刻になる THEN system SHALL 前日の振り返り（ハイライト・一言・次の提案、LIFF の来館ログへのリンク）を LINE の push で本人に届ける
19. system SHALL 送信時刻を海遊館の開館時刻1つで決める。開館時刻はコードに直書きせず設定として持つ（置き場所・休館日と季節の変動の扱いは未決論点1）
20. system SHALL push の文言で、その日に開館していることを断定しない（休館日にも同じ時刻に届きうるため）
21. system SHALL push を1ユーザーにつき1日1通までにする
22. IF 前日に来館が無い、または前日の来館が取り消されている THEN system SHALL 送らない
23. system SHALL 同じ来館の振り返りを二重に送らない（定時実行の再試行・重複起動でも1通。送信済みを記録する）
24. system SHALL ユーザーが LINE から振り返りの push を止める・再開できるようにし、止めている間は送らない（来館の記録と LIFF での表示は続ける）
25. IF push が失敗した（ブロック中・通数上限など） THEN system SHALL 送らなかったこととその理由を記録し、その来館の振り返りは LIFF で見られる状態に保つ。同じ日のうちに何度も再送しない
26. system SHALL 送信件数・失敗件数・止めているユーザーで送らなかった件数をログに出し、通数の消費を後から確認できるようにする
27. system SHALL 定時実行の仕組み（Cloud Scheduler 等）、振り返りの生成を送信の直前に行うか前夜に行うかを Design で決める

### LIFF での表示

28. system SHALL LIFF に来館ログの一覧（新しい順、日付・発見数・ハイライト）を表示する
29. WHEN ユーザーが来館を1件選ぶ THEN system SHALL その日に見つけた生きもの（初回発見の印つき）・クイズの結果・振り返りの一言・次の提案を表示する
30. system SHALL 通算来館回数を表示する
31. system SHALL 来館当日でも、LINE の「きょうのまとめ」と LIFF の来館ログからその日の途中経過（発見・クイズの集計）を見られるようにする。途中経過はコードの集計だけで作り、エージェントの振り返りは翌日の確定版で付ける（併用。未決論点2）
32. system SHALL LIFF または LINE から来館を取り消せる導線を用意する。取り消しの書き込みは LIFF から Firestore に直接せず、バックエンド経由で行う
33. system SHALL 来館ログを本人だけが読めるようにし（`request.auth.uid == userId`）、LIFF からの書き込みは今どおりすべて拒否する

### プライバシー・セキュリティ

34. system SHALL 位置情報の座標を Firestore・ログに保存しない（今の方針を維持）
35. system SHALL 来館ログに写真そのもの・写真の URL を保存しない（初版は写真を出さず、図鑑の公式画像で見せる）
36. system SHALL クイズの出題中の正解（`pendingQuiz`）を来館ログに書かない。回答済みの正誤だけを残す

### 互換性

37. system SHALL 今の LINE の操作（写真→識別→図鑑登録、クイズ、位置情報→最寄り水族館、駅からの水族館調査）を変えずに動かす。来館ログへの書き込みが失敗しても、本来の応答は返す
38. IF 過去のデータから復元できる来館も無いユーザーである THEN system SHALL 来館ログを空として扱い、エラーにしない

## スコープ外（将来の拡張）

- **海遊館以外の館の来館**（関西15館のマスタからの選択・申告、館ごとの開館時刻、複数館に行った日のまとめ方）。来館の記録に館 ID を持たせることで後から足せるようにしておく
- 海遊館以外の館の生きものの識別・図鑑登録（`animalMaster` の拡張）
- 位置情報からの来館の自動判定（未決論点4の結論しだいで、確認の入口として使うかを決める）
- 思い出動画の生成（#787）
- 来館当日の閉館後など、翌日の開館時刻以外の自動 push
- ユーザーが撮った写真の来館ログへの表示（写真とユーザー・日時の紐づけ、署名付き URL）
- 年パスの有効期限・入館回数の管理、館の公式システムとの連携
- ダイビングのログ
- 他人との共有・ランキング

## 未決の論点

1. **海遊館の開館時刻をどこに持つか・休館日と季節の変動をどう扱うか**
   - 置き場所 案a（推奨）: `kansai-aquariums.json` の海遊館の項目に通常の開館時刻（例 `openTime`）を足す。館ごとのマスタに置くので、他館を足すときもそのまま使える。値は実装時に公式サイトで確認して入れる
   - 置き場所 案b: 環境変数（例 `VISIT_DIGEST_SEND_TIME`）。デプロイし直さずに変えやすいが、館ごとに持つ形にはならない
   - 置き場所 案c: Cloud Scheduler の起動時刻そのもの。最も簡単だが、コードから時刻が見えず、他館へ広げにくい
   - 変動の扱い（推奨）: 休館日・季節の変動は扱わず、通常の開館時刻で毎日送る。文言は「今日も開いとる」のように開館を断定しない（受け入れ基準20）。休館日に送らない対応は、休館日の一覧を手で持つ必要があるため将来の拡張にする
2. **当日に見られる導線（「きょうのまとめ」・LIFF）を残すか**: 推奨は併用。当日はコードの集計だけの途中経過をいつでも見られ、翌日の開館時刻の push でエージェントの振り返り（確定版）が届く。push だけにすると、当日に「今日は何を見つけた？」を確かめる手段が無くなる
3. **申告を当日だけにするか**: 推奨は当日だけ（「今日行った」のボタン1つ）。過去の日付も申告できるようにすると、日付の入力が要り、翌日の push の対象外の来館が増える
4. **位置情報を使うか**: 推奨は今回は使わない。申告で「行った日」は記録でき、位置情報の流れ（最寄り水族館の案内）を変えずに済む。代案は、位置情報を送って最寄りが海遊館で一定距離内（目安1km）のときだけ「今日の来館として記録する？」のボタンを添える（申告の入口を増やすだけ。座標は保存しない）
5. **push を既定でオンにするか**: 推奨は既定でオンにし、その人の最初の来館が記録されたときに一度だけ「翌日の開館時刻にまとめが届く。止めたいときは〇〇」と告知する。代案は最初に「届けてほしい？」と聞いて、選んだ人にだけ送る（通数は減るが、届く人が少なくなる）
