# 要件定義: 駅・地名を起点にした水族館の質問にADKマルチエージェントで答える

## 背景・スコープ

LINE Bot が受け取った自由文（`text`）のうち、駅・地名を起点に水族館を尋ねる質問に、ADK のマルチエージェント（水族館調査エージェント）で答える。水族館マスタ（関西15館）を RAG として参照し、駅すぱあと MCP（`MCPToolset`）で駅・到達範囲を調べる。

現状、`text` はすべて `characterChat`（Gemini の雑談応答）に流れ、水族館や駅の知識を使えない。位置情報メッセージ → 最寄り水族館は [#789](../789-nearest-aquarium/requirements.md) で実装済み（駅すぱあと REST 直呼び）で、本specでは変更しない。

ADK + ekispert MCP の実測（`backend/scripts/try-ekispert-agent.ts`）:

- 所要時間は約8.9秒。位置情報フローの時間予算（最大7秒）に収まらないため、自由文の質問用に分離する
- `search_routes` で渡した `time` が抜け、`searchType` が `departure` ではなく `plain` になる。**LLM に任せるとツール引数がぶれる**

対象:
- 自由文からの「駅・地名を起点にした水族館の質問」の受信と、水族館調査エージェントの起動
- 水族館マスタを RAG として使う水族館の特定・絞り込み
- 駅すぱあと MCP による駅の特定・到達範囲探索
- 待ち時間への対応（「調べ中」を先に返し、完了後に push で本命を返す）

対象外（本specでは扱わない）:
- 位置情報メッセージ → 最寄り水族館（#789）のフロー、および `ekispert.ts` / `nearestAquarium.ts` の挙動変更
- 関西以外の水族館、魚（生きもの）情報、営業時間・料金・混雑状況
- 雑談・生きもの質問など、駅・地名を起点にした水族館の質問以外の自由文（従来どおり `characterChat`）

## ユーザーシナリオ

| # | 発話の例 | 期待する動き |
| --- | --- | --- |
| S1 | 「大阪駅に近い水族館」「神戸駅から近い水族館調べて」 | 起点駅を特定し、マスタの水族館を近い順に最大3館返す。起点駅は水族館の玄関口駅でなくてよく、言い回しの違いも同じ質問として扱う |
| S2 | 「彦根駅から1時間くらいで行ける水族館」 | 起点駅から60分以内に行ける駅を探し、マスタの水族館と突き合わせて、**上限に近い（遠い）ものから順に**最大3館返す |

## 受け入れ基準（EARS形式）

### 入口と振り分け

- WHEN ユーザーが `text` を送り、駅・地名を起点に水族館を尋ねる意図と判定される THEN system SHALL 水族館調査エージェントを起動する
- WHEN 上記の意図でない `text` を受信する THEN system SHALL 従来どおり `characterChat` で応答する
- WHEN `location` / `image` / `postback` を受信する THEN system SHALL 既存の挙動を変えない（`location` は #789 のフローのまま）
- system SHALL #789 の位置情報フローの公開関数・返信内容・挙動を変更しない

### 待ち時間への対応

- WHEN 水族館調査エージェントを起動する THEN system SHALL replyToken で「調べ中」を先に返信し、完了後に push メッセージで回答を送る
- IF エージェントの処理が失敗する、またはタイムアウトする THEN system SHALL push で「調べられなかった」旨を返す（無応答にしない）

### S1: 駅に近い水族館

- WHEN 「〇〇駅に近い水族館」の質問を受ける THEN system SHALL 駅すぱあと MCP で起点駅を特定し、その座標とマスタの各館の座標との直線距離（Haversine）で近い順に最大3館を選ぶ
- system SHALL 返信に、水族館名・府県・起点駅からの直線距離（km）・玄関口駅・アクセス・公式URLを含める
- system SHALL 「に近い」「から近い」「調べて」「ある？」などの言い回しの違いを同じ質問として扱う
- system SHALL 起点駅を、水族館の玄関口駅に限らず、駅すぱあとで特定できる任意の駅にできる（例: 神戸駅）

### S2: 所要時間で行ける水族館

- WHEN 「〇〇駅から△時間（分）くらいで行ける水族館」の質問を受ける THEN system SHALL 駅すぱあと MCP の `search_ranges` で、起点駅から指定時間以内に行ける駅を取得する
- system SHALL 「くらい」を幅としてではなく上限として扱い、指定時間を `upperMinutes` の上限とする（例: 1時間 → 60分）
- system SHALL 取得した駅とマスタの `stationCode` を突き合わせ、該当する水族館を**所要時間の長い順**（指定時間の上限に近いものから）に最大3館返す
- system SHALL 返信に、各館の起点駅から玄関口駅までの所要時間（電車のみ。玄関口駅からのバス・徒歩は含まない）を含め、その旨を明記する
- IF 指定時間内に行ける水族館がない THEN system SHALL その旨を伝え、時間を延ばす提案をする
- IF 指定時間が `search_ranges` の許容範囲（10〜200分）外 THEN system SHALL 範囲内に丸めたうえで、その旨を伝える

### 起点駅の名寄せ（曖昧さはエージェントが判断する）

- system SHALL 起点駅名の表記ゆれ・同名の駅（例: 「神戸」「大阪」「彦根駅」）の解決を、駅すぱあと MCP の `get_stations` を使うエージェントの判断に委ねる。曖昧さ解消のためのルールをコード側に持たない
- system SHALL 返信に、実際に起点として使った駅名を含める（判断が誤っていた場合にユーザーが気づけるようにする）
- system SHALL 起点駅の駅コードを、`get_stations` のツール結果に書かれた値だけから決める（推測で作らない）

### ツール引数の決定性・回答の根拠

- system SHALL `gcs`（`wgs84`）・`types`（`["train"]`）など、結果を左右するツール引数をコード側で固定し、LLM の判断に依存させない（実測で `searchType` と `time` がぶれたため）
- system SHALL 水族館名・玄関口駅・駅コードにマスタの値だけを使い、マスタに無い水族館・駅を答えに含めない
- system SHALL 所要時間にツール結果の値だけを使い、推測で数値を作らない
- WHERE 水族館の玄関口駅からバス・徒歩の移動が必要な館 THE system SHALL マスタの「駅からのアクセス」を併記する

### 返信の見た目

- system SHALL 本命の回答を、#789 と同様の Flex カルーセル（最大3館）とジンベエのセリフで返す
- system SHALL 所要時間を取得できなかった項目は、Flex から行ごと省き、説明はセリフで補う

### 運用・セキュリティ

- system SHALL 駅すぱあとのアクセスキーを Secret Manager で管理し、リポジトリにコミットしない（#789 と同じ `EKISPERT_API_ACCESS_KEY`）
- system SHALL ユーザーの発話を Firestore・ログ等に永続化しない
- system SHALL 既存の LINE 署名検証を通過したリクエストのみ処理する

## 未確定事項（設計フェーズで詰める）

- 自由文の振り分け方法（意図判定を軽量な LLM 呼び出しで行うか、エージェントの最初の判断に含めるか）と、誤判定時に雑談応答へ戻す方法
- エージェント構成（ルートエージェント＋水族館調査 sub-agent）と、マスタ RAG の実装方式（15館なので、ベクトル検索ではなく `FunctionTool` での JSON 検索で足りるか）
- 駅すぱあと MCP のセッション管理（毎回接続して `close()` するか）と、エージェント全体のタイムアウト値
- LINE の push メッセージ通数の上限と、無料枠への影響
- `search_ranges` の返り値に、駅ごとの所要時間が含まれるか（S2 の並べ替えと表示に必要。実呼び出しで確認する）。含まれない場合の代替（例: 該当館だけ `search_routes` で補う）
