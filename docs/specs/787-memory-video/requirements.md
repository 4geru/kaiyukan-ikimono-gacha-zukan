# Requirements — 思い出振り返り動画（送られた写真から自動生成）

Issue: [#787](https://github.com/4geru/tweet-bookmark/issues/787)（関連: [#779](https://github.com/4geru/tweet-bookmark/issues/779) いきものガチャ図鑑）

## 目的

水族館やお出かけで撮った家族・友達との写真から、その日の思い出を振り返る短い動画を自動で作って届ける。提出記事・紹介動画の「これから作りたいこと」の1つ目（記事: 「家族や友達との思い出をシェアする: 水族館で撮った写真から、思い出の動画を自動で作る」）に当たる。

**初版は 1:1 トークで Bot に送られた写真を素材にする**（2026-10-08 ユーザー決定）。Issue 本文の「LINE グループの写真から」は、データモデルと基準を拡張できる形にしておき、後から対応する（「拡張時の基準」節）。

審査基準との対応:

- **課題の新規性と有効性**: 撮ったまま埋もれる写真を、誰も編集しなくても「その日の1本」にまとめる。図鑑づくりで送った写真の延長で、水族館の1日がそのまま思い出になる
- **自律性・エージェントらしさ**: どの写真を使うか・並べ方・ナレーションをエージェントが状況を見て理由付きで決める。上限・同意・公開範囲・外部送信はコードで縛る。判断の過程を記録して後から追える
- **実装品質と拡張性**: 素材の範囲（1:1 → グループ）と描画方式（FFmpeg／外部の動画生成モデル）を差し替え可能にし、呼び出し回数と費用に上限を設ける

## ユーザーの決定（2026-10-08）

| 論点 | 決定 |
| --- | --- |
| 素材の写真 | 1:1 トークで送られた写真。グループに拡張できる形にしておく |
| 同意の取り方 | 本人が有効にする（オプトイン）。グループ拡張時は「誰かが有効化＋各自が自分の写真を拒否できる」 |
| 写真の選び方 | エージェントが代表カットを選ぶ（3〜12枚） |
| 作る時刻 | 21:00 JST に起動。0:00〜20:59 JST に送られた写真をその日の分とする |
| グループのいきもの写真 | 初版の対象外（グループ自体が拡張時）。拡張時も図鑑連携は別 Issue |
| 振り分け方法 | Gemini Vision（既存と同じ `gemini-2.5-flash`）で「いきもの（案内板）／思い出／使わない」の3値＋理由 |
| 動画の作り方 | **FFmpeg on Cloud Run Jobs のみ**（2026-10-08 ユーザー決定）。Gemini で構成、Gemini TTS でナレーション、FFmpeg で静止画（ズーム・パン）＋字幕＋音声をつなぐ。協賛 API（GMI Cloud・YouCam API）は使わない |

## 前提（コードで確認済み）

- Webhook は 1:1 トークのイベントしか扱わない。`getUserId` が `source.type === "user"` 以外を `undefined` にし、`handleEvent` の先頭で捨てている（`server.ts`）。グループの写真は今は受け取っていない
- 1:1 トークの画像は、`replyMessage` で「解析中」を即返信 → `blobClient.getMessageContent` で取得 → GCS 保存と生きもの識別を並列実行 → 結果を `pushMessage` で送る（`server.ts` の `handleImageMessage`）。**写真1枚につき push を1通すでに使っている**。識別できなければ「見つからない」Flex を push する
- 画像はすべて GCS の `line-images/${messageId}.jpg` に `contentType: "image/jpeg"` 固定で保存される（`storage.ts`）。保存期間・削除の処理は無く、誰の写真か（userId）・いつ送られたかも保存していない。バケットは非公開（`kaiyukan-gacha-hackathon-images`、CLAUDE.md）
- 画像の判定は Google Cloud Vision API ではなく Gemini Vision（`identifyFish.ts`、`gemini-2.5-flash`）。案内板の文字を読んで海遊館のマスタと照合する用途
- 重い処理は Webhook に 200 を先に返してから fire-and-forget で動かす（`/webhook`）。Webhook 再送時の冪等性は未対応（CLAUDE.md の TODO「低」）
- Firestore のセキュリティルールは LIFF から本人の `users/{uid}` 配下の一部だけ読み取りを許し、それ以外はすべて拒否（`firestore.rules`）。Bot は Admin SDK
- 動画生成の既存ナレッジは**ローカル実行のみ**: `video/` は Remotion で紹介動画を作り、ナレーションは Gemini TTS（`scripts/generate-voice.ts`）、BGM は Lyria（失敗時はフリー素材）。この Mac では Remotion の Chrome が起動しないため、インストール済み Chrome を使う（`video/Makefile`）。Cloud Run 上で動画をレンダリングする仕組みは今は無い
- 姉妹プロジェクト（`project-aruaru-zukan/remotion/scripts/aruaru/CLAUDE.md`）の知見: Gemini 生成画像に日本語を描かせない（文字はレンダリング側で描く）、生成済みの画像は再生成しない（課金回避）
- 2026-09-18 の Fable 設計ヒアリングでは、本機能は「価値提供の軸が違うので即カット推奨」とされ、ハッカソン提出版からは外れている（`docs/2026-09-18-22-40-fable-design-hearing.md`）

### 前提（協賛 API の調査、2026-10-08 時点・Web で確認）

ハッカソン公式の Support スポンサー推奨サービス（利用有無は審査に影響しない）のうち、動画づくりに関係しうる2つを調べた。

**YouCam API（Perfect Corp.）**

- 確認できたこと:
  - 美容・肌解析・ヘア・ファッション・ジュエリーと、生成系の画像・動画機能を持つ非同期のタスク型 REST API。ドキュメントのカテゴリに Skin analysis / Virtual try-on / Image editing / Video generative AI がある。ホスト型 MCP サーバー（Beauty / Fashion / Creators）もある（[Quick Start](https://docs.perfectcorp.com/develop/quick_start_guide)、[docs](https://docs.perfectcorp.com/)、第三者のまとめ [api-evangelist/perfect-corp](https://github.com/api-evangelist/perfect-corp)）
  - 料金はユニット制（サブスクは月次付与・60日まで繰越、従量は購入から1年有効、消費したユニットは戻らない）。1ユニットの単価・機能ごとの消費量は公開ページで確認できず、API コンソールで見る形（[利用規約](https://www.perfectcorp.com/perfectbeauty/youcam/terms-of-service-api)）
  - データの扱い（[利用規約](https://www.perfectcorp.com/perfectbeauty/youcam/terms-of-service-api)）: アップロードと生成物は原則セッション完了後30日保持。明示の同意が無ければサービス改善に使わない。写真の**顔の幾何情報を識別することがあり、写っている全員の同意を取るのは利用者の責任**。サービスは13歳未満向けではない。タスクと入出力を消す API（`POST /s2s/v2.0/task/delete`）がある（検索結果の要約で確認）
- 未確認: 「複数の写真から1本の動画を作る」機能の有無（Video generative AI の具体的な機能名・入出力）、ユニット単価、データの保管地域
- 評価: 中心は美容・ファッション。思い出動画の「写真の選定・つなぎ・ナレーション」に直接当たる機能は確認できなかった。顔の幾何情報を扱う前提で全員の同意が要り、子どもの写真を送る用途とは相性が悪い

**GMI Cloud**

- 確認できたこと:
  - OpenAI 互換 API で 100 以上のモデル（LLM・画像・動画・音声）を呼べる推論プラットフォーム。動画は text-to-video と image-to-video があり、Kling・Veo・MiniMax・PixVerse・Seedance など。料金はリクエスト単位で、動画は 1リクエスト約 $0.02〜$0.50（例: Kling Image2Video V1.6 Standard $0.056、Veo 3.1 preview $0.40）。契約・最低利用量なし（GMI Cloud 公式ブログの記載。数か月前の情報のため最新は [コンソール](https://console.gmicloud.ai/) で要確認。[Best Managed Platforms for AI Inference APIs](https://www.gmicloud.ai/en/blog/best-managed-platforms-for-ai-inference-apis)、[MaaS](https://www.gmicloud.ai/en/models/maas)）
  - 推論インフラは米国・台湾・シンガポール・タイ・日本・マレーシア。共有推論ではプロバイダのポリシーが全テナントに適用され、ゼロ保持は専有デプロイ等で**設定するもの**として案内されている（[How Is Data Managed During AI Inference?](https://www.gmicloud.ai/en/blog/data-managed-during-ai-inference)）
- 未確認: 共有推論（MaaS）での入力・出力の既定の保持期間、学習・改善への利用の有無（[プライバシーポリシー](https://www.gmicloud.ai/en/privacy-policy) の本文を取得できず）、各動画モデルの提供元への再送信の有無
- 評価: 「写真から短い動画クリップを作る」役割には使える。ただしデータの扱いが未確認のうちは、家族・子どもの顔写真を送る根拠がない

## 想定ユーザー

- **写真を送る人（主）**: 水族館やお出かけで家族・友達と撮った写真を Bot に送る人。その日の夜に動画を受け取り、見る・保存する・自分でシェアする
- **写っている人（子どもを含む）**: 自分で同意できないことがある。顔写真の扱いに最も配慮が要る
- **運用者（開発者）**: 費用と push 通数を見張り、問題があれば止める
- （拡張時）**グループの参加者**・**グループに Bot を追加する人**

## 受け入れ基準（EARS）

### データモデル（グループに拡張できる形）

1. system SHALL 思い出用の写真ごとに「所有者（送った人の LINE userId）」「共有範囲（`user:<userId>`、拡張時は `group:<groupId>`）」「送られた日時」「振り分け結果と理由」「保存期限」を持つ
2. system SHALL 同意を共有範囲ごとに持つ（初版は `user:<userId>` だけ）。写真をプールに入れるか・動画を作るか・どこに届けるかは、共有範囲と同意だけで決める
3. system SHALL 動画1本ごとに「共有範囲」「対象日」「使った写真の ID」「配信先」を持ち、配信先を共有範囲から導く（1:1 なら本人、拡張時はそのグループ）

### 受け付けと振り分け（1:1）

4. WHEN 本人が機能を有効にする（リッチメニューまたは「思い出動画をつくる」） THEN system SHALL 写真を何に使うか・保存期間・写っている人への配慮のお願い・止め方を伝え、同意を記録する。有効にするまで写真をプールしない
5. WHEN 有効なユーザーから画像が届く THEN system SHALL 既存の生きもの識別と並行して、Gemini Vision で「いきもの（案内板）／思い出／使わない」に振り分ける
6. system SHALL 既存のフロー（写真→識別→候補選択→図鑑登録・クイズ）の動作と push 通数を変えない。振り分けのために push を増やさない
7. IF 写真が「思い出」に振り分けられ、生きもの識別で候補が無かった THEN system SHALL 既存の「見つからない」の push の代わりに「思い出に入れた」旨のメッセージを同じ1通で送る（通数は変えない）
8. IF 振り分けがどちらとも決まらない、または失敗した THEN system SHALL その写真を思い出として扱わず、プールにも入れない（迷ったら使わない）
9. system SHALL 機能を有効にしていないユーザーの写真を振り分けにかけない（今までどおり識別だけ）

### プライバシーと同意（コードで縛る）

10. WHEN 本人が停止（例:「思い出動画やめて」）を送る、または Bot をブロックする THEN system SHALL 機能を止め、プール済みの写真と未配信の動画を削除する
11. system SHALL プールした写真と生成した動画を、配信後の保存期間（7日）を過ぎたら自動で削除する。保存期間は基準4で伝えた値と一致させる
12. system SHALL 写真と動画を非公開のまま扱う。動画の配信に URL を使う場合は期限付きの署名付き URL にし、全体公開のバケット（`kaiyukan-gacha-hackathon-public-assets`）には置かない
13. system SHALL 動画を、その共有範囲の配信先以外に送らない。別のユーザー・共有範囲の写真を混ぜない
14. system SHALL 写真の中身（顔・人物の説明）をログに出さない。ログに残すのは件数・ID・判断の理由（人物を特定しない言葉）だけにする
15. system SHALL 顔認識による個人の識別（誰が写っているかの名寄せ）をしない
16. system SHALL 写真・動画をモデルの学習やデモ素材に流用しない。デモには運用者が自分で用意した写真だけを使う
17. IF エージェントが不適切と判断した写真（裸・けが・他人の個人情報が読める画面など）がある THEN system SHALL その写真を動画に使わず、使わなかった件数だけを記録する
18. system SHALL 写真を Google Cloud（Gemini を含む既存の送信先）以外の外部サービスに送らない
19. IF 外部サービスに写真を送った THEN system SHALL 送り先・写真 ID・削除要求の結果を記録し、提供元に削除 API があれば生成後に呼ぶ

### 写真の選定・構成・ナレーション（エージェントが判断する）

20. WHEN 1日分のプールから動画を作る THEN system SHALL エージェントに写真（候補）を渡し、使う写真（3〜12枚）・並べる順番・各カットの一言・全体のタイトルを理由付きで決めさせる
21. system SHALL エージェントに「似た写真の重複を避ける」「ブレ・暗い写真を避ける」「時系列の流れが分かる」「その日に図鑑に登録した生きものとつなげる」を判断材料として与える
22. system SHALL ナレーション・字幕をキャラクター（ジンベエ名誉教授・カワウソ助教授）の口調で作り、写っている人の名前・年齢・関係の推測を入れない
23. system SHALL 日本語の字幕は生成画像に焼き込ませず、レンダリング側で描く（既存ナレッジ）

### 上限・失敗時（コードで縛る）

24. IF エージェントが選んだ写真が12枚を超える、または3枚を下回る THEN system SHALL コードで12枚に丸める（超過は理由の順位で切る）。候補が3枚に満たない日は動画を作らない
25. system SHALL 動画の長さを上限内（推奨: 60秒以内）に収める
26. system SHALL 1共有範囲・1日あたりの動画を1本までにし、呼び出し回数に上限を設ける（振り分けは1枚1回、選定・構成は1日1回、TTS はカット数＋タイトル分まで）
27. system SHALL 1共有範囲・1日にプールする写真を最大50枚にし、超えた分は振り分けもしない
28. system SHALL 外部の有料 API の利用額に月の上限を設け、超えたら外部の生成を使わず FFmpeg だけで作る
29. IF エージェントが時間内に構成を返さない、または失敗した THEN system SHALL 規則（時系列順・12枚まで・定型のタイトル）で構成し、規則で作ったことを記録する
30. IF 動画の生成そのものが失敗した THEN system SHALL 失敗を通知する push を送らず、失敗を記録して翌日に持ち越さない

### 配信と push 通数

31. WHEN 21:00 JST の定時バッチが動画を作り終える THEN system SHALL 配信先に1回の push（キャラの一言＋動画を1リクエストにまとめる）で届ける
32. system SHALL 1配信先に送る思い出動画の push を1日1回までにし、push する前に当月の送信可能数を確認する。残りが足りなければ配信を止めて記録する
33. system SHALL 動画が作られない日（候補3枚未満・同意なし）には何も送らない

### 可観測性

34. system SHALL 動画1本ごとに「候補の写真数・使った写真数・使わなかった理由の内訳・エージェント／規則のどちらで決めたか・丸めの有無・呼び出し回数と外部 API の利用額・処理時間・配信結果」を記録する
35. system SHALL 記録から写真そのものや人物の情報を辿れないようにする（写真 ID は保存期間の削除と同時に記録からも消すか、匿名化する）

### 拡張性・運用

36. system SHALL 構成（使う写真・順番・一言・ナレーション）と描画を分け、描画方式（FFmpeg／外部の動画生成モデル／Remotion）を差し替えられるようにする
37. system SHALL 機能全体を環境変数1つで止められるようにする

### 拡張時の基準（LINE グループ対応。初版では実装しない）

38. WHEN Bot がグループに追加される THEN system SHALL 機能の説明・写真の使い道・保存期間・止め方を投稿し、誰かが有効にするまで写真をプールしない。説明に「子どもが写る場合は保護者が有効にする」ことを書く
39. system SHALL 写真を投稿した本人が自分の写真の利用を拒否できるようにする。拒否した人の写真はプールに入れず、プール済みのものは削除する
40. WHEN 参加者が停止を送る、または Bot がグループから退出させられる THEN system SHALL そのグループの機能を止め、プール済みの写真と未配信の動画を削除する
41. system SHALL グループ写真への返信は replyMessage だけを使い（通数に数えない）、返信もその日の最初の1枚だけにする
42. system SHALL グループへの push が「人数分」の通数として数えられることを前提に、基準32の確認を人数分で行う
43. system SHALL グループで受けたいきもの写真は図鑑パイプラインに流さず、思い出の素材にもしない（図鑑連携は別 Issue）

## スコープ外

- LINE グループの写真の受け付け（「拡張時の基準」は設計のみ。データモデルは基準1〜3で拡張できる形にする）
- 顔認識・人物の名寄せ、「この人だけの動画」
- 動画の SNS への自動投稿・公開ページ
- BGM の自動生成（既存の Lyria は使わず、固定の素材から選ぶ）
- YouCam API の利用（思い出動画に当たる機能が確認できず、顔の幾何情報の扱いで写っている全員の同意が要るため）
- GMI Cloud など外部の動画生成モデルの利用（2026-10-08 ユーザー決定で FFmpeg のみ。将来、人物の写っていない写真に限って使う案は、データの保持期間・学習利用を確認してから別途検討）
- 動画の編集 UI（LIFF で写真を差し替える等）
- 年パス来館ログ（「これから作りたいこと」の2つ目、別 Issue）
- 既存の `line-images/` に溜まっている過去の写真の遡及利用（同意前の写真なので使わない）
