→ 本記事の方針:

3. 冒頭に **TL;DR（3 行）** を置く
4. **数字を 1 つ足す**: `search_ranges` の生のレスポンスと、FunctionTool が LLM に返す内容のサイズ（文字数、可能ならトークン数）を並べる。LLM を介さず MCP を直接呼ぶだけで測れる。**MCP のアクセスキーで実際に呼ぶ必要があるため、実施するかはユーザーに確認する**

### 8.9 秒と引数のぶれ

どちらも、最初の検証スクリプト `try-ekispert-agent.ts`（MCPToolset に任せ、**経路探索 `search_routes` まで呼ぶ版**）で測った値。現在の FunctionTool 版と同じ処理を比べた before/after ではなく、FunctionTool 版の所要時間は計測していない。

→ 記事では次のように書く。

- 「最初の検証（MCPToolset にすべて任せ、経路探索まで行う版）で見えた問題」として紹介する
- 8.9 秒は「位置情報フローの時間予算 7 秒に収まらなかった」という判断材料として出す。**FunctionTool にしたから速くなった、とは書かない**
- FunctionTool 化の主な理由は「引数のぶれ」と「巨大なレスポンス」であり、速度ではないことをはっきりさせる

### 旅の図（全体像）

mermaid の `flowchart LR` で、段階単位に描く。クラス名・メソッド名・ツール名は書かない。

```
LINE で質問 → 水族館の質問か判定 → 「調査中」をすぐ返す
  → 起点の駅を特定（駅すぱあと） → 行ける駅を調べる（駅すぱあと）
  → 水族館リストと突き合わせ → キャラのセリフ付きで結果を送る
```

- 「駅すぱあと」を通る段階と「自前のデータ・コード」の段階を色分けする（LLM／MCP／コードの役割分担が図でも分かるように）
- 色分けは `classDef` で行い、Zenn のプレビューで色が反映されるか確認する（反映されない場合は、段階名に「駅すぱあと」「コード」と書いて区別する）
