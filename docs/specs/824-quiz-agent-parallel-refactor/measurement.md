## 原因の切り分け（`scripts/probe-quiz-single-call.ts`）

並列にしても 1 カテゴリ分の生成 1 回が長いため、全体が縮まなかったと見て、1 カテゴリ（ジンベエザメ・豆知識）の生成 1 回を設定を変えて 3 回ずつ測った。

| 設定 | 所要（秒、3 回） | 思考トークン（3 回） |
| --- | --- | --- |
| `gemini-2.5-flash`（既定） | 15.0 / 12.9 / 11.2 | 2438 / 2120 / 1663 |
| `gemini-2.5-flash`（`thinkingBudget=0`） | 1.9 / 3.3 / 7.5 | 0 / 0 / 0 |
| `gemini-flash-latest`（既定） | 9.2 / 10.1 / 11.8 | 610 / 698 / 646 |

出力トークンはどの設定も 71〜162 で、時間を決めているのは出力ではなく**思考（thinking）トークン**とみられる。クイズ 1 問は約 80 トークンしか出力しないのに、既定では 1600〜2400 トークン考える。

- 含意: 「呼び出し回数×1 回の長さ」で改善前の遅さを説明するモデルは当たっておらず、並列化の下限は「最も遅い 1 回」（約 11〜15 秒）＋「選ぶ 1 回」（約 9〜11 秒）≒ 25 秒前後で、実測とほぼ一致する。縮めるには 1 回の長さ（思考の量）を減らす必要がある。
- 未実施（ユーザー判断待ち）: `thinkingBudget=0`（または軽量モデル）を B・W に適用した場合の全体時間、およびその品質（問題の質が下がらないか）。本計測には含めていない。
- 注意: 設定ごとの回数は 3 回で、ばらつきが大きい（thinkingBudget=0 は 1.9〜7.5 秒）。

## 計測の限界

- 回数が少ない（各 3 回）。中央値は参考値。
- 改善前の失敗が多く、成功した回だけで集計しているため、改善前の所要時間は少ない標本（計 3 回）。
- 方式 B は Gemini API 直接、W は ADK 経由（`LlmAgent`）で、経路が違う。W が B より遅い原因は切り分けていない。
- 候補数が 13 の条件のみ。8 件条件、品質（カテゴリ間の被り・グラウンディング照合）は未計測。
