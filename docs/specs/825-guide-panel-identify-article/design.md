### TL;DR（3 行案）

- 案内板の写真は Gemini に「文字を読む」ことだけを任せ、どの種か決めるのは 243 種全件を走査するスコアリングで行った
- 誤りは「配列順バグ」「データ欠落」「OCR 誤読」の 3 種類に分かれ、直るのは配列順バグだけだった
- 長さ比の足切りでは「カサゴ→タカサゴ」を防げない。confidence を返して UI に委ねる設計と、その限界を書く

## 数値の扱い: 案の比較と推奨

事実: 既存記録に集計した正解率はなく、サンプル 20 枚の「内容」列もパネルの要約で逐語的な正解ではない（`docs/research/guide-panel-sample-images.md`、Fable レビュー 3 節）。`images/guide/` に jpeg は 20 枚あり、ファイル名の `o-`/`x-` は修正前の結果に基づく接頭辞。

| | 案 1: 事例ベース（数値なし） | 案 2: 正解データを作り直して計測 | 案 3（推奨）: 決定的な部分だけ数値化＋事例ベース |
| --- | --- | --- | --- |
| 内容 | 既存の再検証記録の事例だけで書く | 20 枚の正解種名を写真から確定し、各 3 回実行して正解率を出す | 事例ベースを主軸に、Gemini を呼ばずに再現できる数字だけ足す |
| 必要なもの | なし | Gemini API キー、Firestore 接続、正解データ作成（人手） | 案 3a は Firestore（または `animalMaster` のダンプ）のみ。3b は API キーが必要で任意 |
| 再現性 | 記録どおり | 非決定的。試行回数の設計が要る。正解データ作成の判断が結果を左右 | 3a は決定的 |
| リスク | 「本当に効いたのか」が弱い | 20 枚中 9 枚は他館の可能性があり、母数の意味づけが難しい。正解率が低く出ると主張が弱まる | 小 |
| 工数 | 小 | 大 | 小〜中 |

### 推奨: 案 3

- **3a（必須・API 不要）: 照合ロジックだけを固定入力で比較する。** Gemini の出力は変動するが、照合部分は決定的。記録に残っている誤マッチ事例（ハリセンボン、ウツボ、ツバメウオ、シマアジ、ハナゴイ、カサゴ）を「抽出された名前」の入力として固定し、旧ロジック（`Array.find`）と現行ロジックの結果を表にする。「何がどう変わったか」を、LLM のぶれ抜きで示せる。長さ比（例: カサゴ 3 / タカサゴ 4 = 0.75、シマアジ 4 / マアジ 3 = 0.75、ハナゴイ 4 / アカネハナゴイ 7 ≈ 0.57、ウツボ 3 / モヨウタケウツボ 7 ≈ 0.43）は算術で出せる。旧ロジックの再現は記事用の小さなスクリプトで行う（後述）
- **3b（任意・API キーが必要）: 正解データを使わない安定性の計測。** 20 枚 × 3 回実行し、「抽出された名前の集合が 3 回で同じか」「候補が 0 件／high／low のどれか」を数える。正解の定義が要らないので、正解データ作成の問題を避けつつ「OCR は実行ごとに揺れる」を数字で言える。出すなら実行日・枚数・回数・正解の定義（本件は「正解率ではなく、3 回で抽出結果が一致した割合」）を併記（requirements 基準 3）
- 正解率（案 2）は本記事では行わない。載せない場合は基準 4 に従い、画像ごとの事例にとどめる
- thinking 無効化の効果（「数秒〜十数秒」）は、3b を行う場合のみ `thinkingBudget` あり/なしで所要時間を測って載せる。行わない場合は「コードコメントでは遅くなると書いている」程度にとどめるか、触れない

### スクリプト案（`scripts/` 配下に残す。使用後も削除しない）

| スクリプト | 役割 | 入出力 |
| --- | --- | --- |
| `backend/scripts/compare-matching-logic.ts`（3a） | 固定の抽出名リストを旧ロジック・現行ロジックの両方に通し、結果と長さ比を表で出す | 入力: 事例の抽出名（スクリプト内に定数）。出力: 抽出名 / 旧ロジックの結果 / 現行ロジックの結果と confidence / 長さ比 |

実装上の注意:
- 現行の `identifyFish.ts` は `evaluateFieldMatch` 等を export しておらず、抽出結果は `console.log` のみ。3a・3b は既存コードを変更しない前提だと、(a) 照合ロジックの抜粋をスクリプト内にコピーする、(b) ログ行 `[identifyFish] extractedSpecies:` をパースする、のどちらかになる。コピーは現行と乖離する恐れがあるので、実施時にユーザーへ「`identifyFish.ts` に最小限の export を足してよいか」を確認する（要判断）
- 旧ロジックの再現は、Fable レビューの記述（「完全一致か部分一致かを区別せず先頭から探す」）に基づく。コードの履歴で確認できなければ「レビュー記録に基づく再現」と明記する

## 旅の図（全体像）

mermaid の `flowchart LR` で段階単位に描く。クラス名・メソッド名・関数名・モデル名は書かない。

```
案内板の写真が届く
  → 写っている種名を読み取る（和名・学名・英名のリストにする）【Gemini】
  → 243 種すべてと照合して点をつける【コード】
  → 確信度（高い／低い）をつける【コード】
  → 同じ種をまとめて候補として返す【コード】
  → 候補を LINE で見せる
```

- #823 の方針に合わせ、役割（Gemini／コード）は `classDef` の色分けに頼らず、段階名に【Gemini】【コード】と書いて区別する（`classDef` が Zenn で反映されるかは未確認。メモリ記録の Slidev では mermaid の `classDef` が無視された事例があるが、Zenn は別なのでプレビューで確認し、反映されなければ段階名のみで区別）
- 補助として、照合の中の「1 件の抽出名が 243 種を順に通る」様子を、模式図で 1 枚（mermaid か表）で示す: 抽出名 → 243 種それぞれと比べる → 完全一致 > 長さ比の高い部分一致 > 足切り → 最良の 1 件

## スコアリングの説明方針

読者に伝える順序は「点のつけ方 → 全件走査 → confidence → 重複のまとめ」。抜粋は 4 ブロックに絞り、それ以外は文章で説明する。コード抜粋はすべて「（簡略化）」と注記し `// ...` で省略を示す（基準 2）。

| 抜粋 | 見せる狙い | 元の位置 |
| --- | --- | --- |
| 部分一致の比較（`a === b` なら完全一致、含み合いなら長さ比 `min/max`）。正引き・逆引きを同じ基準で扱う点 | 「完全一致」と「部分一致」を分け、部分一致には長さ比という点をつける | `evaluateFieldMatch` 64〜76 行 |
| 全件走査と最良選択（`for (const animal of animals)`、足切り `ratio < 0.5`） | 配列順に依存しない。早期 return しない | `findBestMatchingAnimal` 98〜120 行 |
| 閾値と confidence（0.5 / 0.75、exact は常に high） | 閾値の意味。UI に判断を委ねるための 2 段階 | 61〜62、122〜125 行 |
| 同一種の重複を 1 件にまとめ、high を優先 | パネルに複数名がある場合に同じ種が二重に出ない | `identifyFishFromImage` 176〜197 行 |

補足で触れる事実（コードで確認済み）:
- 和名・学名・英名の 3 フィールドそれぞれで照合し、最良の 1 つを採用する（`evaluateAnimalMatch`）
- 正規化は小文字化と空白・中黒・句読点の除去のみ（`normalize`）
- 生の抽出結果を `console.log` に残している（OCR 誤読とロジックの誤りを切り分けるため）。クエ→ヒメフエダイは、クエが 243 種に完全一致で存在するのに誤った候補が出たため、Fable レビューで「おそらく Gemini 側の誤読」と判定された。記事では「おそらく」のまま書く（ログで確認した確定事実ではない）

誤った書き方を避ける点:
- 閾値 0.5・0.75 の根拠は「Fable レビューで絶対長（3 文字未満）がほぼ機能しないと指摘され、長さ比にした」まで。0.75 という値自体を最適化した記録はないので、「最適値」とは書かない

## 誤マッチ事例の扱い

事実は `docs/2026-09-19-00-15-fable-identify-accuracy-review.md` と `docs/research/guide-panel-sample-images.md` の再検証と一致させる（基準 5・6）。

### 原因の 3 分類（章 5 の表）

| 種類 | 事例 | マッチング改善で直るか |
| --- | --- | --- |
| 配列順バグ（ロジック） | ハリセンボン→ヒトヅラハリセンボン。正解は 243 種にあるが、劣る部分一致が配列の前方にあり `Array.find` が先に採用 | **直った**。全件走査＋完全一致を優先し、再検証で完全一致・high になった |

注意: ツバメウオ→ヒメツバメウオの再検証後の結果は記録に明記がない（修正後の記録で言及されているのは 09 の「シマアジ→マアジ」）。記事に載せる前に実施（3a または再実行）で確認し、確認できなければ書かない。

### 見せ方: カサゴ→タカサゴ

- 位置づけ: 長さ比フィルタ導入で**新たに**生まれた誤マッチ。「タカサゴ」⊃「カサゴ」、比 0.75 ちょうどで high になる（`>=` のため）。意味的に別の魚であることは文字列の長さからは分からない
- 記事での扱い: 失敗事例として章 6 の中心に置く（要件は「載せる前提」）。「直らなかった」「直すなら `classification` で絞る／語頭一致のみ許容するなど別の手段が要る」と書くが、後者は**未検証の案**であると明記する
- 記述の注意: 記録上、17 のパネル内容は「広島湾七大海の幸（オニオコゼ、マナガツオ等）」の要約で、カサゴがパネルに書かれていたかどうかの逐語的な裏付けは記録にない。「カサゴと読まれて」の部分は、再検証記録の記述（Gemini の抽出が「カサゴ」→「タカサゴ」にマッチ）を引用する形で書き、写真で確認していないことを注記する（3b で抽出名を保存できれば確定できる）

## 写真を載せない代わりの見せ方

権利が未確認の海遊館等の掲示物は載せない。次の 4 種で代える。

1. **文字起こし風の再現例（自作）**: パネルのレイアウト別に、抽出結果の JSON と照合結果を並べる。パネルの文面は転載せず、記録にある種名のみ使う。例（2 行構成の表）:

   | パネルのレイアウト（模式） | Gemini の抽出（和名） | 照合結果 |
   | --- | --- | --- |
   | 4 種が縦に並ぶタッチパネル形式 | コウウンテグリ / マガキガイ / インドカエルウオ / モヨウタケウツボ | モヨウタケウツボは 243 種にない |
   | 帯状に 5 種が並ぶ水槽パネル | （記録にあるのは照合後の 4 件のみ: タマカイ、ギンガメアジ、イヌザメ、ヤジリエイ） | 4 件 |

   抽出結果そのものは記録にない画像が多い（記録されているのは照合後の候補）。抽出名は 3b を実施して保存するか、記録にある範囲に限る。**記録にない抽出名を想像で書かない**
2. **模式図**: パネルのレイアウト 4 種（単独紹介／複数種の帯・タッチパネル／図鑑形式／見出し＋名札）をテキストの枠図（mermaid か表）にする。これはプロンプトに書かれている分類で、事実の裏付けがある
3. **レスポンスの JSON 例**: `{ "species": [ { "japaneseName": ..., "scientificName": ..., "englishName": ... } ] }`。スキーマはコードどおり
4. **照合の結果表**（章 4・5）: 抽出名 → 旧ロジック → 現行ロジック → 長さ比

海遊館の公式データ（種名・画像 URL）は、取得元は `kaiyukan.com`（`toAbsoluteImageUrl` の組み立てから確認できる）と事実の範囲で書き、公式画像は転載しない（基準 14）。243 種データの取得・整備の詳細（#780）は書かない。
