# Requirements — 解説記事: 案内板写真から生きものを特定する（Gemini Vision＋243種スコアリング）

Issue: [#825](https://github.com/4geru/tweet-bookmark/issues/825)（親: [#821](https://github.com/4geru/tweet-bookmark/issues/821)）

## 目的

水族館の案内板（解説パネル）の写真から生きものを特定する仕組み（`backend/src/identifyFish.ts`）を題材に、**Gemini Vision には「文字を読む」ことだけを任せ、「どの種か決める」のは海遊館 243 種（Firestore `animalMaster`）との全件照合・スコアリングというコードで行う**設計を、Zenn 記事として公開できる状態にする。あわせて、OCR の読み取り揺れ・誤マッチをどう見つけ、どこまで直せて何が直せなかったかを正直に書く。

## 前提

- 下書きはまだない。ゼロから書く（新規ファイルを `articles/` 配下に作る。ファイル名は Design で決める）
- 投稿先は Zenn（`published: false` のまま作業し、公開はユーザーが判断する）
- 素材（確認済みの事実）:
  - `backend/src/identifyFish.ts`: `gemini-2.5-flash`、`responseSchema` による JSON 出力（和名・学名・英名の配列）、`thinkingBudget: 0`、`animalMaster` 全件を走査、`exact` / `partial` の区別、部分一致は長さ比 `min/max` が 0.5 未満なら除外、0.75 以上で `high`、未満は `low`、同一種の重複は 1 件にまとめて `high` を優先、抽出結果の生ログ出力
  - `backend/scripts/batch-identify-guide.ts`: `images/guide/` の jpeg を順に識別するバッチ（出力は `O/X`・件数・ファイル名・候補と confidence）
  - `backend/scripts/repeat-identify.ts`: 指定画像の識別結果を出す（同一画像の複数回実行用）
  - `docs/2026-09-19-00-15-fable-identify-accuracy-review.md`: 誤マッチの原因切り分け（配列順バグ、データ欠落、OCR 誤読）と改善案
  - `docs/research/guide-panel-sample-images.md`: サンプル 20 枚の内容、修正前の結果、修正後の再検証（2026-09-19）
- 既存の記録には「N 枚中 M 枚正解」のような**集計した正解率はない**。あるのは画像ごとの結果と、疑わしい誤マッチの個別事例のみ（サンプルの正解データも「パネルの要約」で、逐語的な正解ではないと記録に明記されている）
- シリーズ構成: #822（ハッカソン提出記事）が概要、本記事が実装詳細、#823（駅すぱあと MCP × ADK）・#824（クイズエージェント）が兄弟記事

## 想定読者

- Gemini などのマルチモーダル LLM で画像から文字を読み取るアプリを作っている、TypeScript が読めるエンジニア
- 「LLM の出力をマスターデータと突き合わせたいが、誤マッチや揺れで困っている」人

## 受け入れ基準（EARS）

### 内容の正しさ

1. WHEN 記事にコード・パラメータ・閾値・モデル名を載せる THEN system SHALL `backend/src/identifyFish.ts` の現行コードと一致させる（`gemini-2.5-flash`、`thinkingBudget: 0`、閾値 0.5 / 0.75、全件スキャンなど）
2. IF 記事中のコード抜粋が実装を簡略化している THEN system SHALL 簡略化が分かる書き方（`// ...` 省略表記など）にする
3. WHEN 精度の数値（正解率・成功枚数など）を載せる THEN system SHALL 出典を再現可能なスクリプトの実行結果（`batch-identify-guide.ts` / `repeat-identify.ts`）にし、実行日・対象枚数・試行回数・正解の定義を併記する
4. IF 再現可能な実行結果の裏付けがない THEN system SHALL 数値を載せず、画像ごとの事例（どの誤りが起き、どう直ったか）の記述にとどめる
5. WHEN 「修正で直った／直らなかった」ケースを載せる THEN system SHALL `docs/research/guide-panel-sample-images.md` の再検証記録と一致させる（ハリセンボンの配列順バグ解消、モヨウタケウツボの 0 件化、ハナゴイの `low` 化、シマアジ→マアジ・カサゴ→タカサゴが `high` のまま残る限界、OCR の実行ごとのぶれ）
6. WHEN 原因を説明する THEN system SHALL 「配列順バグ（ロジック）」「データ欠落（243 種に正解が無い）」「OCR 誤読（Gemini 側）」を区別して書き、どれがマッチング改善で直る／直らないかを明示する
7. WHEN 243 種や Firestore `animalMaster`、Gemini の仕様（`responseSchema`、`thinkingBudget` の効果など）に触れる THEN system SHALL コードまたは公式ドキュメントで確認できる内容のみ書く。「thinking を切ると数秒〜十数秒速くなる」はコードコメントの記述であり、実測値として書く場合は計測し直す
8. IF サンプル画像に海遊館以外の水族館の写真が含まれる THEN system SHALL 「候補 0 件」が不具合ではなくカバレッジ外の可能性があることを書く（サンプルインベントリの前提と一致させる）

### 構成・読みやすさ

9. WHEN 読者が冒頭を読む THEN system SHALL 「Vision には読むだけを任せ、決めるのはコード側の全件スコアリング」という結論と、その理由（OCR の揺れ・近い名前の別種）が分かる
10. WHEN 読者が記事を読み終える THEN system SHALL 「LLM の抽出結果をマスターデータと照合する際の注意点」（全件走査で配列順に依存しない、完全一致を最優先、長さ比で部分一致を足切り、confidence を返して UI に委ねる、生の抽出結果をログに残して OCR 誤読とロジック誤りを切り分ける）を自分のアプリに持ち帰れる
11. WHEN 限界を書く THEN system SHALL 長さ比だけでは意味的な違い（カサゴ／タカサゴ）を区別できないこと、データに無い種は原理的に当たらないことを隠さず書く

### 図

12. WHEN 全体の流れを図示する THEN system SHALL 関数単位のシーケンス図ではなく、段階単位の「リクエストの旅」（写真が届く → 文字を読む → 243 種と照合 → 確信度をつける → 返す、のような粒度）の図にし、クラス名・メソッド名・関数名を図に書かない

### 権利・配慮

13. IF 案内板の写真を記事に載せる THEN system SHALL 海遊館等の掲示物であることへの配慮を行い、掲載可否は Design で決める。権利上の確認が取れない写真は載せず、文字起こし・模式図・自作の再現図で代える
14. WHEN 海遊館の公式データ（種名・画像 URL 等）に触れる THEN system SHALL 取得元と利用範囲を事実の範囲で書き、公式画像そのものを記事に転載しない
15. IF 記事にアクセスキー・トークン・公開していない内部 URL が含まれる THEN system SHALL 削除する

### シリーズとの関係

16. WHEN 記事を書く THEN system SHALL 冒頭か末尾にシリーズ（提出記事 #822、駅すぱあと MCP 記事 #823、クイズエージェント記事 #824）への導線を置く（未公開の記事はリンク先を後で差し替えられる形にする）
17. IF 内容が提出記事（#822）と重複する THEN system SHALL 提出記事は概要、本記事は照合ロジックと精度検証の詳細という分担を守る

### 公開前

18. WHEN 執筆が完了する THEN system SHALL `/article-review` で複数の観点からレビューし、客観的な指摘を反映する

## スコープ外

- `identifyFish.ts` 自体の改善（カサゴ／タカサゴ対策、`classification` での絞り込み、UI の「もしかして」表現など）。記事では「今後の課題」として触れるにとどめる
- 243 種データ（`animalMaster`）の取得・整備方法の詳細（#780 の範囲）
- LINE Bot 全体の構成・LIFF 連携（#822 の範囲）
- Zenn への公開操作

## 未決の論点（ユーザー判断を仰ぐ）

1. **精度の数値を載せるか、計測し直すか**: 既存記録に集計した正解率はない。選択肢は (a) 事例ベースで数値なし、(b) 正解データを写真から確定し直した上で `batch-identify-guide.ts` と `repeat-identify.ts`（例: 各 3 回）で計測し直す。(b) は Gemini API キーが必要で、非決定的なため試行回数の設計も要る
2. **案内板写真を載せるか**: 海遊館の掲示物（他館の写真も混在）の権利が未確認。(a) 写真は載せず文字起こしと模式図のみ、(b) 自分で撮影し許可を確認できたものだけ載せる、のどちらにするか
3. **失敗事例の見せ方**: カサゴ→タカサゴが `high` のまま残るなど、未解決の誤マッチを記事に正直に載せるか（本要件は載せる前提）
4. **コード改善を記事の前に行うか**: 長さ比の限界（0.75 ちょうどで `high`）を直してから書くか、現状の実装を書いて課題として残すか（本要件は後者を想定）
5. **thinking 無効化の効果**: コードコメントの「数秒〜十数秒」を実測し直して載せるか、載せないか
6. **ファイル名・タイトル**: 下書きがないため Design で決めるが、#823 と同様に `articles/` 直下の命名規則で良いか

## 決定事項（2026-10-07 ユーザー回答）

- 案内板の写真は**載せない**。文字起こし・模式図で代える
- 記事の型はシリーズ共通方針に従う: 結果入りタイトル・冒頭 TL;DR・比較は表（`823-ekispert-mcp-agent-article/design.md`「記事の方向性」）
- その他の未決論点は Design で決めて提示する
