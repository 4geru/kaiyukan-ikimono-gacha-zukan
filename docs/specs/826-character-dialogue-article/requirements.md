# Requirements — 解説記事: Message.sender でキャラが掛け合う LINE Bot

Issue: [#826](https://github.com/4geru/tweet-bookmark/issues/826)（親: [#821](https://github.com/4geru/tweet-bookmark/issues/821)）

## 目的

LINE の `Message.sender`（送信元のアイコンと名前の上書き）を使い、**1つの Bot でジンベエ名誉教授とカワウソ助教授が掛け合っているように見せる方法**を Zenn 記事として公開できる状態にする。あわせて、自由文への返事を Gemini でキャラの掛け合いとして生成する部分と、キャラ設定・セリフの決め方を扱う。

## 前提

- 下書きはまだない。**ゼロから書く**（`articles/` 配下に新規作成、`published: false` のまま作業し、公開はユーザーが判断する）
- 素材は以下。記事の事実はこれらで確認したものだけを書く
  - `backend/src/characters.ts`（キャラ名・表情別アイコン URL・`characterLine`。通常の text メッセージにキャラごとの `sender` を付け、1回の返信に複数個並べる方式）
  - `backend/src/characterChat.ts`（自由文を Gemini `gemini-2.5-flash` に渡し、JSON スキーマで 1〜2 行の掛け合い `lines` を返させる）
  - `backend/scripts/try-character-chat.ts`（生成だけを LINE なしで試す確認スクリプト）
  - `docs/charactor/`（`base.md` / `dr-jinbei.md` / `kawauso.md` / `dialogue-scenarios.md`）
  - 呼び出し側は `backend/src/server.ts`（自由文テキストは掛け合いで返信、生成失敗時はジンベエ名誉教授の固定文で返す）
- 実装済みの機能を解説する記事であり、実装の変更は行わない
- シリーズ分担は後述（受け入れ基準 12・13）

## 想定読者

- LINE Messaging API で Bot を作ったことがあり、TypeScript が読めるエンジニア
- 「Bot の返事が単調」「1つの Bot で複数キャラを喋らせたい」「LLM にキャラ口調を守らせたい」と考えている人

## 受け入れ基準（EARS）

### 内容の正しさ

1. WHEN 記事にコード・モデル名・URL 構造・キャラ名・語尾・件数（1〜2 行）を載せる THEN system SHALL `characters.ts` / `characterChat.ts` / `server.ts` と `docs/charactor/` の現行内容と一致させる
2. WHEN `Message.sender` の仕様（指定できる項目、文字数などの制約、アイコン URL の条件、使えるメッセージ種別など）に触れる THEN system SHALL LINE 公式ドキュメントで確認できる内容のみ書き、確認できなかった制約は書かない（記憶や推測で書かない）
3. IF 記事中のコード抜粋が実装を簡略化している THEN system SHALL 簡略化が分かる書き方（`// ...` 省略表記など）にする
4. WHEN Gemini の仕様（`responseSchema`、`responseMimeType` など）に触れる THEN system SHALL 公式ドキュメントで確認できる内容のみ書く
5. WHEN 「動いた」「掛け合いになった」といった実行結果や生成例を載せる THEN system SHALL `scripts/try-character-chat.ts` の実行結果か実機での確認に基づく実物にし、創作したセリフを実出力として載せない（設定資料 `dialogue-scenarios.md` の例は「設定上の例」と明示する）

### 構成・読みやすさ

6. WHEN 読者が冒頭を読む THEN system SHALL 「`sender` で名前とアイコンを差し替え、text メッセージをキャラごとに並べるだけで掛け合いに見える」という結論が分かる
7. WHEN 読者が記事を読み終える THEN system SHALL 次の3点を自分の Bot に持ち帰れる
   - `sender` で複数キャラを出す方法
   - LLM に掛け合いを JSON で返させ、キャラごとのメッセージに変換する方法
   - キャラ設定（口調・役割）の決め方と、それをプロンプトに落とす考え方
8. WHEN キャラ設定とセリフの決め方を書く THEN system SHALL `docs/charactor/` の設定（一人称・語尾・役割分担・メイン／サブ担当）が、実装の `SYSTEM_INSTRUCTION` と固定セリフにどう反映されたかを対応づけて示す
9. IF 生成失敗時のフォールバック（固定セリフで返す）を載せる THEN system SHALL 「無応答にしない」設計意図をコードの事実の範囲で書く

### 図

10. WHEN 全体の流れを図示する THEN system SHALL 関数単位のシーケンス図ではなく、段階単位の「リクエストの旅」の図（例: ユーザーの自由文 → キャラの掛け合いを考える → キャラごとの吹き出しに分ける → LINE に返す）にし、クラス名・メソッド名・ファイル名を図に書かない
11. WHEN LINE のトーク画面のスクリーンショットを載せる THEN system SHALL ユーザー名・アイコン・LINE ID・個人情報が写らないようにする（撮影用アカウントを使う、または加工して隠す）。載せるかどうか自体は「未決の論点」で決める

### シリーズとの関係

12. WHEN 記事を書く THEN system SHALL 冒頭か末尾にシリーズ（提出記事 #822、関連記事 #823・#824）への導線を置く（未公開の記事はリンク先を後で差し替えられる形にする）
13. IF 内容がハッカソン提出記事（#822）と重複する THEN system SHALL 本記事は実装の詳細（`sender` の使い方・掛け合い生成・キャラ設定）、提出記事は概要という分担を守り、概要の説明は #822 に任せてリンクする

### 公開前

14. WHEN 執筆が完了する THEN system SHALL `/article-review` で複数の観点からレビューし、客観的な指摘を反映する
15. IF 記事に API キー・トークンなどの秘密情報や、公開していない内部 URL が含まれる THEN system SHALL 削除する（アイコン画像の公開バケット URL を載せるかは未決の論点）

## スコープ外

- `characters.ts` / `characterChat.ts` / `server.ts` のリファクタ・機能追加（例: 表情の自動選択の改善、会話履歴の保持）
- キャラ画像の新規生成・差し替え
- 他のキャラ（海遊館以外）への一般化の議論
- Zenn への公開操作
- 提出記事（#822）の本文執筆

## 未決の論点（ユーザーに判断を仰ぐ）

1. **トーク画面のスクリーンショット**を載せるか。載せる場合の撮影方法（撮影用アカウント／加工）。載せない場合は、図とセリフのテキスト引用で代替するか
2. **キャラ画像（生成画像）の公開可否**。記事に画像を載せてよいか、載せるなら画像生成ツールの利用規約・権利表記の確認が必要か。載せない場合、`sender.iconUrl` に使う公開バケットの URL をコード抜粋にそのまま出してよいか（ダミー URL に置換するか）
3. **`docs/charactor/` 設定の引用範囲**。設定資料はリポジトリ内資料のため、記事にどこまで転載するか（口調・役割の要点のみか、セリフ例も載せるか）
4. **実機での掛け合い例の用意**。受け入れ基準 5 のため、`try-character-chat.ts` の実行結果を何本載せるか（質問の種類・件数）。API キーが使えない場合は実行結果なしで構成するか
5. **シリーズ内の公開順と相互リンク**。#822 が先に公開されるか、リンクを後で差し替える前提でよいか
6. **コードの表情ファイル名の揺れ**（`dr-jinbe-happy.jpeg` とスペルが異なる箇所がある）を記事で触れるか。実装修正はスコープ外のため、触れるなら「実際の URL に合わせている」程度に留めるか

## 決定事項（2026-10-07 ユーザー回答）

- LINE のトーク画面のスクリーンショットは**載せる**。ユーザー名・アイコンなど個人情報は隠す
- 記事の型はシリーズ共通方針に従う: 結果入りタイトル・冒頭 TL;DR・比較は表（`823-ekispert-mcp-agent-article/design.md`「記事の方向性」）
- その他の未決論点は Design で決めて提示する
