### キャラ設定と実装の対応（requirements 基準 8 用）

| 設定資料（`docs/charactor/`） | 実装での反映 |
| --- | --- |
| カワウソ: 一人称ボク、語尾「〜っす！」、元気なファシリテーター役 | `SYSTEM_INSTRUCTION` に「テンポよく元気で賑やかなファシリテーター役。語尾は〜っす」。固定セリフも「〜っす」 |
| ジンベエ: 一人称ワシ、語尾「〜じゃ」「〜のう」、長老役 | `SYSTEM_INSTRUCTION` に「重厚で知識豊富な長老役。語尾は〜じゃ・〜のう」。固定文も「むむ、〜のう」 |
| 設定資料は一人称・二人称・口調・ルールまで書く（YAML で persona 定義） | **実装は語尾と役割のみに圧縮**（一人称・二人称は `SYSTEM_INSTRUCTION` に入れていない） |
| 掛け合いのメイン／サブ担当（UC ごとに分担） | 自由文返信では分担を決めず、LLM に 1〜2 行で任せる（実装では `kawauso`/`dr-jinbei` どちらも先頭になり得る） |
| 「事実は共通データソースに従う」 | 自由文では `SYSTEM_INSTRUCTION` の「事実に基づかない内容は断定せず『詳しくは分からんのう』」で代替。**自由文経路はデータソースを参照しない**（正確さの保証はない、と正直に書く） |

## 記事の方向性

### タイトル候補（結果入り）

1. 「LINE Bot 1つで2キャラが掛け合う — `sender` を付けた text を並べるだけで、Flex もいらなかった」（推奨）
2. 「Bot の返事が急に会話になった: `Message.sender` と Gemini の JSON 出力でジンベエとカワウソを喋らせる」
3. 「1回の返信にキャラを2人並べる — `sender` と Gemini の構造化出力で作る掛け合い LINE Bot」

「数字」は 2 キャラ・最大 2 行・表情 3 種など実装由来の値のみ使う（実測値のない「◯倍」は入れない）。

### 冒頭 TL;DR（3 行案）

- `Message.sender` で名前とアイコンを差し替え、text メッセージをキャラごとに並べるだけで、1 つの Bot が掛け合っているように見える
- 返事は Gemini に「キャラ・表情・セリフ」の JSON（1〜2 行）で返させ、そのまま `sender` 付きメッセージに変換する
- 生成に失敗した時は固定セリフで返し、無応答にしない

### 対象読者節（冒頭、TL;DR の直後）

requirements「想定読者」をそのまま使う（LINE Bot 経験あり・TypeScript が読める・返事が単調／複数キャラ／LLM にキャラ口調を守らせたい）。

### 旅の図

mermaid `flowchart LR`。段階単位、クラス名・メソッド名・ファイル名・ツール名は書かない。

```
ユーザーが自由文を送る
  → 掛け合いを考える（Gemini: 誰が・どの表情で・何を言うかを 1〜2 行の JSON で）
  → 行ごとに吹き出しを作る（名前とアイコンをキャラに差し替え）
  → 1 回の返信にまとめて LINE へ返す
      ↳ 考えるのに失敗したら: ジンベエ名誉教授の固定セリフ 1 つを返す
```

### 設定資料（`docs/charactor/`）の引用範囲

- 載せる: プロフィール表の「一人称/二人称」「基本口調」「役割」の要点、persona YAML の `endings`（語尾）と `rules` の 1〜2 行

| # | 画面 | 目的 | 載せる章 |

- ユーザー発言（質問文）も写るので、個人情報・位置情報を含む質問を使わない。**Bot の返信に出るキャラのアイコン・名前は、公開前提のものなので隠さない**（隠さないとスクショの意味がなくなる）

### 実機での掛け合い例（受け入れ基準 5）

- `try-character-chat.ts` を **4 本**（スクショ ③④ と対応する 2 本 + 引数なし既定「ジンベエ教授は何歳ですか？」+ 雑談 1 本）実行し、出力をそのまま載せる。Gemini の出力は毎回変わるため、記事には「ある 1 回の出力」と明記する
- 実行には `GEMINI_API_KEY` が必要。**実行はユーザーが行うか、実行してよいかの確認が必要**（Design 段階では実行していない）。キーが使えない場合は「動かしてみる」の章を、実機スクショ（既存の会話があれば）のみで構成する
