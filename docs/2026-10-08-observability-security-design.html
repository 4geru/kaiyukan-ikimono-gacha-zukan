エージェントの判断ログと安全対策 — 設計レビュー

審査基準「自律性が適切に管理・制御され、可観測性やセキュリティへの配慮を持った、信頼できる動作をするか」への対応。まず Cloud Logging（Firebase と同じ GCP プロジェクト）のログから作り、その上に記録の見える化とガードを足す。

2026-10-08 作成 ／ 仕様: docs/specs/832-observability-security/requirements.md・design.md ／ 提出締切 2026-10-15

0結論

Cloud Run の出力を1行 JSON にし、エージェント1回ごとに「何を検討し・どのツールを呼び・何を選び・なぜか・コードがどこで止めたか・何秒何トークンか」を1行（agent_run）で残す。ログは運用と集計、Firestore は利用者ごとの記録と LIFF 表示、と役割を分ける。

締切までに フェーズ1（ログ・指標・アラート）とフェーズ2（判断の記録と LIFF 表示）を全部、フェーズ3 は入力の区切り・停止スイッチ・時間切れ時の切り替え・再送の二重処理防止・写真の7日削除まで入れるのを推奨。BigQuery は使わず Log Analytics で足りる。

1今あるもの／足りないもの

今あるものは README.md に別途まとめる。本 Issue は右側だけを扱う（コードで確認済み）。

今あるもの（README 側）

  • 実行ユーザーの最小権限（UID 10001、非 root）
  • 出力スキーマでの制約（カテゴリは候補だけの enum、雑談は2キャラ×3表情×1〜2行）
  • 候補外カテゴリを候補内に差し替える関数
  • Secret Manager・LINE 署名検証
  • Firestore ルール（本人だけ読める・正解の入った出題中データは読めない）
  • 位置情報を残さない／正解をエージェントに渡さない
  • 駅エージェントの25秒タイムアウト

足りないもの（本 Issue）

  • 判断の記録: クイズの理由・全候補は回答時に消える。駅エージェントは何も残さない
  • ログ: 文字列だけ。項目で絞れず、1件のやり取りをつなぐ ID も無い
  • ガードの件数: 差し替え・時間切れは警告文だけで数えられない
  • 指標と監視: 失敗率・p95・トークン・アラートが無い
  • 入力: 自由文を区切らず渡す・長さ上限なし
  • 回数上限・停止スイッチ: 無い（止めるには再デプロイ）
  • Webhook 再送の二重処理: 防いでいない（回答だけは防止済み）
  • 写真: 非公開バケットに無期限で残る
  • 依存: npm audit の指摘・ベースイメージのダイジェスト未固定

3ログの形（フェーズ1）

共通の項目

項目内容何に使う
severityINFO / WARNING / ERROR重大度で絞る・ERROR は Error Reporting に乗る
message人が読む一文（日本語）一覧での見やすさ
event種別（下の表）絞り込みの主キー
logging.googleapis.com/traceCloud Run のトレース ID1件のやり取り（Webhook→返信）をまとめて表示
runId / agentエージェント1回の ID ／ quiz・station・quiz_level・quiz_pool1回の判断の全部（ツール→判断→ガード）をつなぐ。#829・#831 と共通
userIdHashLINE userId の SHA-256 先頭8桁同じ人の流れをつなぐ（生の ID は出さない）
latencyMs所要時間p95・時間切れの監視
versionCloud Run のリビジョン名どの版の判断か（プロンプト変更の前後比較）

イベントの種類

eventいつ主な項目
webhook_receivedWebhook 1件ごと種類・postback の action・再送か
agent_runエージェント1回の終了（必ず1行）outcome・model・promptVersion・ツール回数・入出力トークン・decision（候補・選択・理由）
tool_callツール1回tool・ok・件数・個人情報の無い引数（分数・by=family など）
guardコードが介入したguard（差し替え・時間切れ・規則へ・切り詰め・回数上限・停止・形式不正）・action
llm_callエージェント以外の LLM 1回purpose（意図判定・雑談・写真の識別…）・トークン・入力の文字数
webhook_duplicate再送を止めたイベント ID のハッシュ
reply_sent返信・push を送ったreply か push か・件数・ok

個人情報をログに載せる／載せない

情報Cloud LoggingFirestore（本人だけ）
LINE userIdハッシュ SHA-256 先頭8桁ドキュメントのパス（既存）
自由文（雑談・駅の質問）出さない 文字数と切り詰めたかだけ残さない
エージェントが確定した起点駅・分数出す残す
写真出さない 識別結果（生きもの ID・確からしさ）だけ残さない（GCS で7日後に削除）
位置情報出さない（既存方針）残さない
エージェントの理由・候補出す残す（選ばれなかった候補の選択肢・正解は残さない）

指標・アラート・費用

ログベースの指標（5つ）

  • エージェントの実行回数（agent × outcome）→ 失敗率
  • 所要時間の分布 → p95
  • トークン量の分布 → 費用
  • ガードの介入回数（種類別）
  • LLM 呼び出し回数（用途 × 成否）

アラート・画面

  • 15分で失敗率 30% 超（5件以上）→ メール
  • ERROR が15分で10件超 → メール
  • ダッシュボード1枚（4グラフ）
  • 集計は Log Analytics の SQL。BigQuery への書き出しは不要

保存期間と費用

  • ログ: 30日（既定・無料）。取り込み月 50 GiB まで無料、想定は月 0.3 GB 程度
  • Firestore の駅の記録: 30日で自動削除
  • 再送防止の記録: 1日で自動削除
  • アラート条件は少数なので月数十円以内の見込み

4フェーズ分け

フェーズ1 ／ ログ

まず追えるようにする

  • 1行 JSON・trace・runId・ハッシュ
  • agent_run・tool_call・guard・llm_call
  • 指標5つ・アラート・ダッシュボード
フェーズ2 ／ 記録の見える化

利用者にも見えるようにする

  • クイズ: 理由・検討したカテゴリ・runId を回答履歴に引き継ぐ
  • 駅: 利用者ごとの判断の記録（30日）
  • LIFF「なぜこの問題？」
フェーズ3 ／ ガード

止められるようにする

  • 入力の区切り・200文字上限・レッドチーム試験（15〜20件）
  • 停止スイッチ（Firestore で1分以内に効く）
  • クイズの45秒時間切れ → 決まった手順で出題
  • 再送の二重処理防止・写真の7日削除・ダイジェスト固定
  • 回数上限（1人1日）・npm audit

5締切（10/15）までの推奨範囲と分担

中身締切までに担当依存
T0 ログの土台（1行 JSON・trace・runId・終了時に1行）と Webhook の入口入れるSonnet—
T1 クイズ: 判断ログ・ツール記録・45秒で決まった手順へ・回答履歴への引き継ぎ入れるSonnetT0
T2 駅: 判断ログ・3ツールの記録・利用者ごとの記録とルール入れるSonnetT0
T3 入力の区切りと上限・停止スイッチ・再送防止・LLM 呼び出しの記録入れるSonnetT0
T4 指標・アラート・ダッシュボード・写真の削除ルール・Makefile・ダイジェスト固定入れるHaiku—
T5 レッドチーム試験のスクリプト（試験文と機械判定）入れるHaikuT3（実行のみ）
T6 LIFF「なぜこの問題？」入れるSonnetT1 のデータ形
回数上限（1人1日）余裕があればSonnetT3
npm audit の解消余裕があればHaiku—
T7 Log Analytics 有効化・通知先メール・TTL 適用・デプロイ・デモ録画人ユーザーT0〜T6

T0 で関数の形を決めれば T1〜T4 は並列にできる。T1〜T3 は同じ入口のファイルを触るので、触る処理を分けて順にマージする。

6審査員・デモでの見せ方

Logs Explorer のクエリ

resource.labels.service_name="kaiyukan-gacha-bot"
# ① 判断の一覧

デモ動画（約40秒）

  1. LINE で「クイズ」→ 問題が届く
  2. クエリ④で、実在種の検索 → 8候補・選んだもの・理由・27秒・トークンを並べて見せる
  3. クエリ③で、差し替え・時間切れ・停止の行を見せる（「任せきりにせず、コードが止める」）
  4. ダッシュボード1枚（失敗率・p95・ガード件数・トークン）
  5. LIFF でその問題の「なぜこの問題？」を開く（「判断は本人にも見える」）

ガードの行は本番で自然に出るとは限らないため、停止スイッチを一時的に入れる・評価スクリプトを通すなどで出してよい。

7判断してほしい点

利用者 ID のハッシュ方式

SHA-256 の先頭8桁（#829 と同じ）か、秘密の値を混ぜた HMAC か。

推奨: SHA-256 先頭8桁。LINE userId は推測できない値で、Secret を増やさず #829 と値が揃う。

判断の記録の置き場所

クイズは回答履歴に引き継ぎ＋駅は利用者ごとの agentRuns、か、全部を agentRuns に寄せるか。

推奨: 前者。クイズの判断は「その1問」と一緒に見る方が分かりやすい。選ばれなかった候補の選択肢・正解は残さない（作り置き #831 で後から出題され得るため）。

停止スイッチの置き場所

Firestore の設定ドキュメントか、環境変数か。

推奨: Firestore（60秒キャッシュ）。コンソールで書き換えれば1分以内に効き、再デプロイが要らない。

回数上限と写真の保持期間

回数上限（クイズ30・駅20・雑談100・写真30 回/日）を締切前に入れるか。写真は7日か30日か。

推奨: 回数上限は締切後でよい（停止スイッチで代える）。写真は識別の後で使わないので7日で自動削除。

締切までの範囲

5章の「入れる」すべて＋BigQuery は使わない、でよいか。

推奨: その通り。Cloud Trace へのスパン送信・管理画面・LLM による自動採点はスコープ外。
設計担当: Claude（Opus） ／ 読んだもの: CLAUDE.md・server.ts・quizAgent.ts・stationAquariumAgent.ts・characterChat.ts・firestore.rules・Dockerfile・Makefile・#829 design の 6.5／10 章
